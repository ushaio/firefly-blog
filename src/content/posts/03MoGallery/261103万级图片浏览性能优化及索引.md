## [[FTS5]] 关键词索引

>SQLite 默认的查询是 `WHERE file_name LIKE '%keyword%'` 这种 **子串扫描**：没有索引，每查一次都要把全部行读一遍，也无法排序。资源库到几万张图时，输入框每敲一个字触发一次这种查询，相当于让 UI 卡住。FTS5（Full-Text Search 5）是 SQLite 内置的**全文检索扩展**：它把文本拆成词（token），建立一张“词 → 行号 + 位置”的**倒排索引**，于是 `MATCH '哈苏'` 是一次索引查找 + 打分，而不是一次全表扫描，同时顺带提供相关性排序（`bm25()`）、前缀匹配（`hass*`）、短语（`"a b"`）、布尔（`AND` / `OR` / `NOT`）等能力。`LIKE` 全都给不了。

assets_search表前缀的表

FTS5 的对外身份是**虚拟表（virtual table）**,`CREATE VIRTUAL TABLE asset_search USING fts5(...)` 只向 SQLite 注册了一个模块入口，当查询sql如`SELECT ... FROM asset_search WHERE asset_search MATCH ?` 时，实际运算发生在 fts5 模块里。但模块**必须把状态存到真实磁盘结构上**，于是它按一层命名约定（`<表名>_<后缀>`）在同一个库里创建若干普通表，也就是**影子表（shadow tables）**，即：asset_search_data / _idx / _content / _docsize / _config

| 表                    | 解决什么                                                   | 为什么不能别的表代劳                                                                                                                                                                                                      |
| -------------------- | ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `_idx`               | 倒排索引本体：词 → RowID 列表（含列号与位置，用于短语匹配和 bm25 的 `phrase` 加权） | 这是 FTS5 存在的意义；体积大头也在这，几万条的库通常占索引总量的 70%+                                                                                                                                                                        |
| `_data`              | 每行各列的**原文副本**，按内部块（block）分页存放                          | 命中后要回读文本（谁想直接拿到 `notes` 原文），以及更新单行时需要定位块内位置；块结构才有好的写放大表现                                                                                                                                                        |
| `_content`           | RowID ↔ 内部 docid ↔ 列块 的映射表                             | 对外 rowid 是你指定的 `assets.local_id`，内部还要一层 docid 才能找到块；两者解耦，才不用每次写都重排索引                                                                                                                                            |
| `_docsize`           | 每行**每列的 token 数**                                      | `bm25()` 的长文档惩罚要用字段长度归一化，不然 `notes` 长的图永远排前面                                                                                                                                                                    |
| `_config`            | 虚拟表的持久化配置：`version`（磁盘格式版本）、`tokenize` 等               | tokenizer 是**必须持久化**的，否则同一份索引换个分词器打开就全错；本库这里写的是自定义的 FTS5 tokenizer（见 [store_search.go](/D:/Projects/mo-gallery/emulsion-desktop-v3/local_library/store_search.go:40)），中文要靠它切成 n-gram，默认的 `unicode61` 会把整句中文当一个词 |
| `asset_search_dirty` | **不是** FTS5 的影子表，是本项目自己的队列表                            | 见上一轮说明；它就是为了不让触发器在事务里逐行改索引                                                                                                                                                                                      |



## 两级派生缓存

>描述得有些高级了。**为同一份原始资源，按显示用途生成两档图片：网格缩略图和大图预览**

![](assets/Pasted%20image%2020261103213837.png)

`derivatives.db` >> `asset_derivatives`表
`cache_key`：缓存key
![](assets/Pasted%20image%2020261103210344.png)`variant(previews)` 生成规则 = `asset_id` + `cache_key` 
`variant(thumbnails)` 生成规则 = `asset_id` + `cache_key` 

按照使用场景：

| 档位              | 用途            | 当前尺寸策略                   | 保留策略                   |
| --------------- | ------------- | ------------------------ | ---------------------- |
| `thumbnail`：缩略图 | 资源库网格、列表等快速浏览 | 短边目标 560 px，长边上限 2048 px | 不参与大图预览的容量淘汰           |
| `preview`：预览图   | 详情栏预览、部分看图场景  | 长边上限 2048 px             | 默认容量预算 2 GiB，按最近访问时间淘汰 |

- thumbnails：用于文件浏览
- previews：
	> 用于无法直接浏览图片的文件，如raw、video媒体文件
	1. 大图查看器：RAW 的唯一显示源，以及解码失败时的回退源
	2. AI视觉调用

# 浏览加载性能优化
| 环节 | 已有实现 | 优化目的 |
| --- | --- | --- |
| 首屏数据 | 第一页返回立即展示，再沿游标继续获取剩余页；通过请求编号丢弃过期结果 | 不必等整个查询加载完才能看到照片 |
| 回访缓存 | 对侧栏范围查询保留最多 12 份首屏数据，回到同一范围时先恢复缓存，再请求更新 | 减少来回切换时的等待和空白 |
| 网格渲染 | 普通网格按行虚拟化，只挂载可视范围及额外预取的 5 行；卡片使用 `memo`，结果未变时保留原数组 | 减少 DOM 数量和重复渲染 |
| 图片加载 | 虚拟窗口中的图片直接请求，刻意不再叠加 `loading="lazy"` | 给图片提前加载的机会，减少快速滚动时露白 |
| 缓存复用 | 派生图保存在磁盘；响应同时设置长期、不可变的 HTTP 缓存策略 | WebView 可以复用已有响应，后端也能复用已生成文件 |
| 首次生成 | 同一缓存 key 的请求合并；优先处理选中资源和可见资源，后台预热优先级较低 | 避免重复生成，让当前浏览内容优先完成 |
| 后台写入 | 派生记录使用独立的 `derivatives.db`，并批量提交 | 减少扫描、生成缓存和浏览同时进行时的数据库争用 |
