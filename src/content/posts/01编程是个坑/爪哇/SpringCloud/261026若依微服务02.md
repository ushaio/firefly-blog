> 服务之间是怎么互相调用的——若依微服务篇（二）

# 服务间调用关系

## 一、为什么必须"调用"而不是"直连数据库"

若依微服务的数据库是按服务拆分的：

| 服务 | 数据库 |
| :--- | :--- |
| `ruoyi-system` | `ry-cloud`（用户、角色、菜单、部门、字典） |
| `ruoyi-job` | `ry-job` |
| `ruoyi-workflow` | `ry-workflow` |
| `ruoyi-ai` | `ry-ai` |

拆分库的目的就是**谁的数据谁负责**。别的服务要用用户信息、字典翻译、文件 URL，都不能连别人的库，只能走接口——这就是 `ruoyi-api` 存在的理由。

## 二、`ruoyi-api` 的拆分结构
  
`ruoyi-api` 是一个 `packaging=pom` 的聚合模块，下挂 `ruoyi-api-system`、`ruoyi-api-resource`、`ruoyi-api-workflow` 等子模块。每个子模块内部固定三件套：

```
ruoyi-api-system/
└── src/main/java/org/dromara/system/api/
    ├── domain/            # 跨服务传输的 DTO（如 SysUser、LoginUser、SysDept）
    ├── RemoteUserService.java   # FeignClient 接口声明
    ├── factory/RemoteUserFallbackFactory.java   # 降级工厂
    └── model/             # 返回包装体（LoginUser、R<T>）
```

> [!TIP] 关键点
> `ruoyi-api` 里**只有接口和 DTO，没有实现**。实现永远在被调用方（provider）的 `ruoyi-modules/ruoyi-system` 里，通过 `@RestController` 实现 `RemoteXxxService` 接口。这样消费方编译期只需要依赖 `ruoyi-api-system`，不需要依赖整个 system 服务。

## 三、Feign 调用三步走

### 1. 被调用方实现接口

```java
// ruoyi-modules/ruoyi-system
@RestController
@RequiredArgsConstructor
public class SysUserController implements RemoteUserService {

    private final ISysUserService userService;

    @Override
    @InnerAuth   // 只允许内网调用
    public R<LoginUser> getUserInfo(String username, String source) {
        SysUser user = userService.selectUserByUserName(username);
        ...
    }
}
```

### 2. 调用方引入 api + 开启 Feign

```xml
<dependency>
    <groupId>org.dromara</groupId>
    <artifactId>ruoyi-api-system</artifactId>
</dependency>
```

在启动类或 `ruoyi-common-web` 的自动配置里打上 `@EnableFeignClients(basePackages = "org.dromara")`，Feign 会扫描全包下的 `@FeignClient`。

### 3. 注入并使用

```java
@Service
@RequiredArgsConstructor
public class SysLoginService {

    private final RemoteUserService remoteUserService;

    public LoginUser login(String username) {
        R<LoginUser> r = remoteUserService.getUserInfo(username, "password");
        if (R.isError(r)) {
            throw new ServiceException(r.getMsg());
        }
        return r.getData();
    }
}
```

上面的代码其实就是 `ruoyi-auth` 登录时做的事：**auth 自己不再查用户表，而是通过 Feign 让 system 去查**。

## 四、典型调用链

### 登录链路（最核心的一条）

```
前端 → Gateway(8080)
        │  /auth/login   （白名单，跳过鉴权过滤器）
        ▼
     ruoyi-auth(9210)
        │  ① 校验验证码（create/verify）
        ▼
     ruoyi-system(9201)   ← Feign：RemoteUserService.getUserInfo()
        │  查询 sys_user / sys_role / sys_menu
        │  ② 组装 SysUser + 权限 + 角色
        ▼
     ruoyi-auth
        │  ③ 生成 Token 写 Redis（Sa-Token/RedisTemplate）
        ▼
        返回 token 给前端
```

### 带 token 的业务请求链路

```
前端 → Gateway(8080)
        │  /system/user/list
        │  ④ 鉴权过滤器：查 Redis Token 是否有效、是否有该权限
        ▼
     ruoyi-system(9201)
        │  只处理自己的库
        ▼
       返回
```

> [!WARNING] 网关只做"过路"和"查 Redis"
> 网关不会去调 system 校验权限，而是**自己拿 token 去 Redis 里查缓存好的权限集**（登录时 system 已经把 `LoginUser` 写进 Redis）。这是若依高并发下的关键设计：业务请求一次鉴权，不产生跨服务 RPC。

### 其他常见调用点

| 调用方 | 被调用方 | Feign 接口（示例） | 场景 |
| :--- | :--- | :--- | :--- |
| `ruoyi-auth` | `ruoyi-system` | `RemoteUserService#getUserInfo` | 登录查用户/权限 |
| `ruoyi-auth` | `ruoyi-system` | `RemoteUserService#registerUserInfo` | 第三方登录 / 短信登录自动注册 |
| `ruoyi-system` | `ruoyi-resource` | `RemoteFileService#upload` | 上传头像/附件 |
| `ruoyi-gen` | `ruoyi-system` | `RemoteDeptService`、`RemoteDictService` | 生成代码时读部门、字典 |
| `ruoyi-workflow` | `ruoyi-system` | `RemoteUserService#getUserInfo` | 审批人解析、发起人信息 |
| 任意服务 | `ruoyi-system` | `RemoteLogService#saveLog`（`ruoyi-common-log` 内置） | `@Log` 注解异步落库操作日志 |
| 任意服务 | `ruoyi-system` | `RemoteDictService#getDictLabels`（`ruoyi-common-translation`） | `@Translation` 字典/用户翻译 |

> [!NOTE] 藏在 Common 里的隐式调用
> `ruoyi-common-log` 和 `ruoyi-common-translation` 内部已经写好了 Feign 调用，业务方只写注解。这类调用**不会被业务代码感知**，排查问题时要记得它们也在打 system。

## 五、调用时的鉴权与透传

| 机制 | 说明 |
| :--- | :--- |
| `@InnerAuth` | 服务端注解，校验 `inner-request` 请求头，值来自认证令牌。只允许服务间调用，拒绝外部直接打到 9201 |
| `SecurityUtils.getLoginUser()` | 通过 `sa-token` 从当前请求上下文拿 `LoginUser`，Feign 调用时会自动带 `Authorization` |
| `FeignInterceptor` / `RequestInterceptor` | 在 `ruoyi-common-security` 中实现，把当前 token、tenantId、traceId 复制到出站请求头 |
| `check-same-token: true` | 网关校验请求 token 与 Redis 中该用户 token 一致，防"旧 token 复用"；也意味着**绕过网关直连内网服务会被拒**（L298 也提到） |

```java
// 若依 ruoyi-common-security 的拦截器（示意）
public class FeignRequestInterceptor implements RequestInterceptor {
    @Override
    public void apply(RequestTemplate template) {
        String token = SaHolder.getRequest().getHeader("Authorization");
        if (StrUtil.isNotBlank(token)) {
            template.header("Authorization", token);
            template.header("inner-request", getInnerToken());  // 内网调用凭据
        }
    }
}
```

## 六、同步 vs 异步调用

| 方式 | 场景 | 若依实践 |
| :--- | :--- | :--- |
| **Feign（HTTP）** | 一般服务间调用 | `ruoyi-api` + `@FeignClient`，默认走 Nacos + LoadBalancer |
| **Dubbo（RPC）** | 高频、低延迟、强类型 | `ruoyi-common-dubbo`，`application-common.yml` 里配 `dubbo.registry.address=nacos://...` |
| **消息总线 / MQ** | 解耦、非实时 | `ruoyi-common-bus`（Spring Cloud Bus）做配置刷新；业务异步用 RabbitMQ / RocketMQ / Kafka |
| **定时任务** | 批量同步 | `ruoyi-job`（Quartz）/ `snailjob-server` 调度各服务 |

> 选型原则：**同步强依赖用 Feign，跨服务写操作要加 Seata；能异步的一律异步**，否则 A 挂了 B 也挂，雪崩。

## 七、调用链路的可靠性设计

| 问题 | 若依的应对 |
| :--- | :--- |
| **下游超时** | `feign.client.config.default.connectTimeout/readTimeout`，`ruoyi-common-web` 里有默认值 |
| **下游挂掉** | `fallbackFactory` 降级（在 `ruoyi-api` 的 `factory` 包），返回兜底数据或抛 `ServiceException` |
| **熔断限流** | `sentinel`（网关已引入）；`ruoyi-common-loadbalancer` 做灰度/同机房优先 |
| **分布式事务** | Seata AT 模式，`application-common.yml` 里 `seata.enabled: false` 默认关闭，需要时开启并部署 Seata Server |
| **调用链追踪** | SkyWalking / Micrometer Tracing，`FeignRequestInterceptor` 保证 traceId 跨服务传递 |
| **重试** | 默认**不要给写操作配重试**（幂等风险），查询可配 1 次重试 |

## 九、读代码时的定位方法

想搞清楚某个功能到底调了谁，按这个顺序找最快：

1. 搜 `@FeignClient(name = "ruoyi-system")` —— 这是消费入口；
2. 去 `ruoyi-api-xxx` 找对应接口方法，看注释和参数；
3. 到 `ruoyi-modules/ruoyi-xxx` 里搜 `implements RemoteXxxService` —— 这是实现；
4. 若方法上只有业务注解、看不到 Feign 声明，就查 `ruoyi-common-log` / `ruoyi-common-translation` —— 隐式调用；
5. 最后看 `script/config/nacos/ruoyi-gateway.yml` 的路由表，确认外部入口路径。
