## 一、先划清「同步 / 异步」边界

数万行（1万～10万）已经不适合"点一下按钮、等 3 秒出结果"的同步模型。

| 规模 | 策略 |
|---|---|
| < 2000 行 | 同步，请求内完成 |
| 2000 ~ 5万 | 同步但必须流式（不整表进内存） |
| > 5万 或耗时 > 5s | 异步任务：建任务 → 返回 `taskId` → SSE/轮询进度 → 下载结果 |

线上最稳的做法是**默认异步**，小文件走快速通道。

## 二、导入优化

**1. 解析放工作线程，且必须流式**
- CSV：papaparse 的 `chunk`/`step` 回调，或后端直接流式读
- xlsx：SheetJS 不要 `read()` 整个 buffer 再转 JSON；用 exceljs `stream.xlsx.WorkbookReader`，逐行 `row.eachCell`
- 解析和校验在一个 Web Worker 内做，主线程只收"进度 + 错误行摘要"，否则 UI 直接卡死

**2. 上传层**
- 不要 base64 塞 JSON（体积 +33% 且全量进内存），用 `multipart/form-data`
- 大文件分片上传 + 断点续传；后端边收边拆成临时 CSV，避免整个 workbook 常驻内存

**3. 校验策略：批量通过 + 错误行隔离**
- 先做"轻校验"（列数、类型、必填、长度），失败的行走**旁路**收集（行号 + 列名 + 原因）
- 允许"部分成功"，返回 `成功 N 行 / 失败 M 行 / 错误明细文件`
- 重校验（唯一键、外键）放到入库前的批量查询里，别一行一次 DB 查询 —— 这是最常见的 N+1 性能坑

**4. 入库**
- 批量写：单条 `INSERT` 拼 500~1000 行，或 Postgres `COPY`、MySQL `LOAD DATA LOCAL INFILE`
- 事务分段：每 1000~5000 行一提交，避免一个巨型事务把 undo log 撑爆
- 幂等：带 `batch_id`，唯一键用 upsert（`ON CONFLICT` / `ON DUPLICATE KEY UPDATE`）
- 索引：导入期间可临时禁用非唯一索引，完成后重建

**5. 常见 Excel 坑**
- 文本型数字（身份证/卡号）被读成 `1.23E+17` → 取 raw value 而非 formatted text
- 日期、合并单元格、公式、隐藏空行都要显式处理
- Java 侧：别用 `XSSFWorkbook` 全量，用 EasyExcel / `SXSSFWorkbook`（滑动窗口 flush 到磁盘）

## 三、导出优化

**1. 读：流式游标，禁止 `findAll()`**
- 分页不要用 `OFFSET`（越翻越慢，10万行会退化成全表扫），用 keyset：`WHERE id > :lastId ORDER BY id LIMIT 1000`

**2. 写：流式生成**
- CSV 最简单，直接边查边写响应流
- xlsx 是 zip 容器，**必须**用流式 writer（exceljs `stream.xlsx.WorkbookWriter`、EasyExcel）。全量拼完再写 = 内存翻数倍
- CSV 再 `gzip`，通常能压缩到 1/10，传输时间直线下降

**3. 下载链路**
- 大文件走异步：任务生成到对象存储 → 前端拿签名 URL → 浏览器原生下载
- 不要用 `axios({responseType:'blob'})` 拉几十 MB 再 `createObjectURL`，内存峰值很痛

**4. 前端列表别跟着一起膨胀**
- 导入成功后不要立刻把 10 万行灌进表格；保持服务端分页 + 虚拟滚动

## 四、通用必备项

- **进度反馈**：SSE 优于轮询（行数、百分比、预计剩余）
- **可取消**：长任务要能中止，并清理临时文件
- **限流与并发**：同一用户同时只允许 1 个导入任务，避免打爆 DB
- **可观测**：记录行数、批次耗时、内存峰值、失败率
- **队列化**：导入/导出进任务队列（BullMQ / Celery / 自建表 + 定时扫描），失败可重试，天然隔离资源

## 五、量级参考

10 万行 × 30 列的 Excel：
- 全量 parse 到对象数组 ≈ 300–600 MB 堆内存，Node/浏览器都容易 OOM
- 流式 + 1000 行/批 ≈ 稳定在 30–60 MB
- 入库耗时主要取决于 DB 往返次数，批量 1000 通常能到 1–3 万行/秒（本地），网络 RTT 是主变量
