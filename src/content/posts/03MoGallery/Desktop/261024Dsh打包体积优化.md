# DSH 打包优化：把 2.6 万个文件收成一个归档

用户反馈装 Emulsion 时只要 DSH 跟着一起装，安装进度条就会卡很久。最直接的怀疑是体积过大，测量结果否定了这一点，瓶颈落在文件数上：453 MB 的载荷摊成 25,789 个文件，安装器要为每一个文件走一次 CreateFile、写目录项、再被杀软扫一遍。

DSH 在安装器里不是可选项，它和主程序同属 `SecMain`，所以用户没法"取消勾选"绕过去，要么一起装，要么别装这个版本。这也是为什么必须在打包形态上解决。

这篇文章记录整个排查和改法。第 0 档先做减法，砍掉桌面端根本挂载不上的东西；第 1 档把剩下的目录树收成单个 tar，安装时只写一个文件，解压挪到应用首启并发做。

## 症状：慢在文件数

改之前 DSH 以完整目录树随包，NSIS 里是一句 `File /r`。安装器把 `build/bin/resources/dsh/windows-amd64/` 下所有东西逐个展开到 `$INSTDIR\resources\dsh\`。

三组测量把瓶颈定死在同一台机器上（Windows，Defender 实时保护关闭，真机开保护只会更慢）：

| 测量 | 结果 |
|---|---|
| robocopy 单线程复制整棵未裁剪的 DSH 树（453.0 MB / 25,789 文件） | 65.8 s |
| 静默安装同一个安装器，但完全不带 DSH | 3.1 s |
| 静默安装带 DSH 目录树的版本（已 prune 到 12,708 文件，三次） | 27.4 / 20.9 / 20.3 s |

第一行是不带任何安装逻辑、单纯把 453 MB 离散成 2.6 万个文件复制一遍的代价：65.8 s。第二行是同一份安装器去掉 DSH 后的基线：3.1 s。第三行是加了 DSH 目录树之后的实际安装耗时。后两行相差 17~24 s，就是那一万多个文件换来的。而 453 MB 本身在 SSD 上顺序读只要一秒级，钱全花在几万次小文件创建和杀软逐个扫描上。

所以改法定了：**bytes 不用管，条目数必须降下来**。分两步走，先做减法把能不带的东西去掉，再把剩下必须带的那部分收成一个文件。

## 第 0 档：先裁掉不用的载荷

仓库里本来就有一个 `build/prune-dsh-runtime.mjs`，之前 DSH 下线时一起停掉了。本次把它恢复，接在 `runtime:dsh:stage` 里，`fetch-dsh-runtime.mjs` 拉完依赖就自动裁。

它裁两类东西。

第一类是桌面端从不挂载的平台载荷。DSH 的 npm 依赖里有 `@deepseek-ai/libreoffice-kit-win32-x64`（Office 转 PDF，182.0 MB / 731 文件）和 `sherpa-onnx-win-x64`（语音转写，22.4 MB / 8 文件）。桌面端的 DSH 只跑文本对话和工具调用，这两项能力一次都没被加载过，留着纯占地方。

第二类是运行期根本不读的派生文件：`.map`、`.pdb`、`.d.ts` 等 sourcemap 与类型声明，`.md`、`.rst`、`.txt` 等文档，以及 `README.yaml` 这类包说明，共 12,342 个文件 102.1 MB。

跑完的结果：

```
453.0 MB / 25,789 files  ->  146.5 MB / 12,708 files   (回收 306.5 MB)
82 DSH dependencies intact; entry point present
```

体积掉了 67.7%，文件数掉了 50.7%。脚本最后那句 `verifyDependencies` 是 fail-closed 的断言：裁完要能重新走一遍 `@deepseek-ai/dsh/package.json` 的每个 direct dependency 和入口文件 `lib/bin.js`，缺一个就抛错退出，不会悄悄打出一个装不起来的包。将来要恢复某项能力，从 `PAYLOADS` 数组里删掉对应规则就行。

体积砍掉三分之二，文件数只降了一半。这一步的价值主要在减小安装包体积和磁盘占用，真正要解决的耗时问题还留在后面。

## 第 1 档：单文件归档

既然瓶颈是条目数，那就让安装器只写一个文件。裁完的 12,708 个文件装起来仍然要 20~27 s，这一档才是真正解决问题的地方。

新增 `build/pack-dsh-payload.mjs`，把裁剪后的目录树打成 `dsh-runtime.tar`，输出到 `build/bin/resources/dsh-payload/<platform>/`。打包耗时 4.3 s，产出 156.1 MB。

两个刻意的设计。

**不压缩。** NSIS 本身对安装包做一次 solid LZMA，tar 进去之后再压一遍只会让安装包更大、解压更慢。实测印证了这一点：整个安装包只比不带 DSH 的版本大 31 MB。应用侧解 tar 则是纯顺序写，正好是磁盘最擅长的形态。

**自己手写 ustar 头。** 只用到最朴素的部分：512 字节头、文件名（100 字节）、prefix（155 字节）、八进制 size/mtime、`ustar\0` magic，再加 checksum。目录项不写，符号链接直接拒绝，路径超过 ustar 限制就抛错而不截断，因为截断会解出一堆同名文件。

拒绝符号链接这条是必须的。pnpm 的 `node_modules/.bin` 原本全是符号链接，`fetch-dsh-runtime.mjs` 的 `materializeLinks()` 已经在 staging 阶段把它们实体化了。打包阶段再遇到符号链接说明树不干净，宁可失败也别打进去，否则装到用户机器上会指向一个不存在的位置。

## 首启并发解压

安装器只写一个 tar，解压由应用首次启动时做。新增 `services/agent_runtime/dsh_payload.go`。

流程是：算 tar 的 SHA-256，与标记文件比对，命中就直接用缓存目录；不命中就解到同级的临时目录 `.dsh-extract-*`，全部成功后再 `os.Rename` 整体发布。这样中途崩了、断电了、用户强杀进程了，都不会留下半棵树的缓存，下次启动重来即可。

解压本体是 `tar.NewReader` 按顺序解码，配一个固定 worker 池并发落盘：

- 并发度 `dshPayloadWorkers = 8`，逐文件写盘是纯 I/O 等待，8 个足够打满普通 SSD 的队列深度，又不会在机械盘上退化成寻道抖动。
- 每个 worker 前面只允许积压 `dshPayloadQueueDepth = 4` 条，防止解码侧跑太快把整棵树攒进内存。
- 单文件超过 `dshPayloadFileMemoryBudget = 32 << 20`（32 MB）就不进 worker，退化成当前 goroutine 流式写。node_modules 里最大的原生模块也就 10 MB 级，这个阈值实际上很少触发。

还有个安全点：tar 里的路径必须落在目标目录内。每写一个条目都先检查 `strings.HasPrefix(destination, root+os.PathSeparator)`，越界直接报 `DSH 载荷含越界路径`。Zip Slip 这类问题在自写的归档实现里最容易漏。

解压目标目录是 `%APPDATA%\mo-gallery-desktop\runtime-bundles\dsh-<version>\<platform>`，与 Node 运行时的 `node-runtime-install.json` 那套记账同构。

## 记账与跳过

标记文件 `dsh-payload-install.json` 记四件事：`version`、`platform`、`archiveSha256`、`installedAt`。

下次启动时比对 `archiveSha256`，一致就跳过整个解压。装新版本换了载荷，哈希变了，自动重解。开发构建和旧安装包里没有 tar，`HasDSHPayload` 返回 false，整个函数返回空串，上层继续用原来的目录树路径，不报错。

`EnsureDSHPayloadOnce` 用 `sync.Once` 语义包了一层单飞：启动预热和第一次真正要启动 DSH 可能同时到达，只允许一次解压。这里有个细节，**失败时不置 done**，否则一次磁盘写满就会让这个进程此后永远拿不到 DSH，重启才能恢复。

解开的目录要能被 DSH 运行时认出来。`services/agent_runtime/paths.go` 的 `ResolveDSHRuntimeRoot` 候选列表末尾追加了缓存目录，前提是确实存在单文件载荷（`DSHPayloadRoot` 非空）。`dsh.go` 里加了 `ensureRoot`，在 `Start()` 里于 `bundledCommand()` 之前调用：Root 里没有 `runtime-manifest.json` 就现解一份再覆盖 Root。这样即使启动预热还没跑完、或者用户手快直接发了一条消息，也不会撞上"未找到随包 DSH runtime"。

原有的校验一条没放松：`bundledCommand` 仍然要求 `manifest.Version == dshVersion`、`manifest.Platform == dshPlatformKey()`、`manifest.Entry == dshEntry`，再对入口文件算一遍 sha256 与 `manifest.SHA256` 比对。解压路径变了，校验口径不变。

应用侧接线只有一行，在 `app.go` 的 `ServiceStartup` 里：

```go
go a.prepareDSHPayload()
```

和已有的 `go image.WarmupAVIFEncoder()` 排在一起，后台跑，不阻塞启动。失败只写一条 `dsh_payload_prepare_failed` 日志，不弹窗，因为用户此刻只是想打开软件看照片。

## 安装器侧：File /r 变一个 File

`build/windows/installer/project.nsi` 里 DSH 段重写了，结构照搬旁边 inference 那段已经跑通的写法。

打包脚本 `build/package-windows-installer.mjs` 新增 `dshSource()`，优先找 `dsh-payload/<platform>/dsh-runtime.tar`，有就走 payload 模式；没有则回退到原来的目录树模式。两种模式都在，老流程不会因为新代码挂掉。

payload 模式下传给 makensis 的定义变成 `-DDSH_INCLUDED -DDSH_PLATFORM -DDSH_RUNTIME_MARKER -DDSH_PAYLOAD_SOURCE`，`dshInstall` 段就这几句：

```nsis
dshCheck:
  IfFileExists "$INSTDIR\resources\dsh-payload\${DSH_PLATFORM}\dsh-runtime.tar" dshDone dshInstall
dshInstall:
  RMDir /r "$INSTDIR\resources\dsh-payload"
  RMDir /r "$INSTDIR\resources\dsh"
  !if "${DSH_PAYLOAD_SOURCE}" != ""
    SetOutPath "$INSTDIR\resources\dsh-payload\${DSH_PLATFORM}"
    File "${DSH_PAYLOAD_SOURCE}"
  !else
    SetOutPath "$INSTDIR\resources\dsh"
    File /r "${DSH_FILES}"
  !endif
```

`${DSH_PAYLOAD_SOURCE}` 为空时回退到老的 `File /r`。这条分支在正常发布里走不到，它的作用是让"没有 pack 出 tar 但树还在"的本地构建仍然出一个能装的包，而不是直接编译失败。

中间那句 `RMDir /r "$INSTDIR\resources\dsh"` 是给升级路径准备的。老版本装出来的目录树还在 `resources\dsh`，不清掉的话它和新的 `resources\dsh-payload` 会同时存在，白占 146 MB。`ResolveDSHRuntimeRoot` 的候选顺序里目录树排在缓存目录之前，留着反而会让应用继续读旧树。

整个 DSH 段用 `!ifdef DSH_INCLUDED` 包起来。没有 staging 到载荷时，打包脚本连 `DSH_INCLUDED` 都不传，NSIS 编译期就把整段连同 `.onInit` 里读 `DSHRuntimeMarker` 的代码一起丢掉，只会 echo 一句 `DSH sidecar: not staged, installer ships without DSH`。这样不带 DSH 构建出来的安装包和以前行为完全一致。

## 打包链路的接线

改完代码不等于生效，这条链有三处必须同时接通，缺一处就静默回退。

`Taskfile.yml` 里 `runtime:dsh:stage` 接上 prune，新增 `runtime:dsh:pack`，并在 `package:windows` 的 cmds 里显式调 pack。这里出过一次问题：`runtime:dsh:pack` 任务定义了却没被任何地方调用，本地跑 `package:windows` 会一路"成功"，打出来的却是目录树版本，提速完全没生效。现在这段被 `{{if eq .DSH_AGENT "true"}}` 守卫，关掉 DSH 时会 echo 一句跳过原因。

`package:windows` 的完整调用链是：

```
wails3 task package:windows      (Taskfile.yml:224)
├─ deps: build  → build:windows → 重编 emulsion.exe + runtime:dsh:check
└─ cmds:
   1. check-dsh-runtime.mjs          校验 staging 的目录树完整（tar 的来源）
   2. pack-dsh-payload.mjs           树 → resources/dsh-payload/<platform>/dsh-runtime.tar
   3. check-inference-runtime.mjs
   4. generate webview2bootstrapper
   5. package-windows-installer.mjs  dshSource() 看到 tar 就走 payload 模式
```

`package:windows` 不含 `runtime:dsh:stage`，它假设树已经在本地。全新机器或换 DSH 版本之后，要先 `runtime:dsh:install` 再 `runtime:dsh:stage`，否则第 1 步就直接失败。

`.github/workflows/release.yml` 的 `windows-release` job 在 prune 之后加了同样的 pack 步骤。macOS 和 Linux 是顺带改的：`bundle:darwin` 本来就 `cp -R resources/` 整个目录，载荷自动跟着进 `.app`；Linux 的 `package:linux` 从 tar 里带上 `resources/dsh-payload`，rpm 的 `%files` 也从 `/usr/lib/emulsion/dsh` 改成 `/usr/lib/emulsion/dsh-payload`。

## 结果

同一台机器、同一份安装器，每次都是"杀进程 → 删目录 → 删注册表项"的全新状态，静默安装：

| | 安装包体积 | 安装耗时 | 磁盘落地 |
|---|---|---|---|
| 不带 DSH | 136.5 MB | 3.1 s（一次） | 605 文件 |
| DSH 目录树，已 prune（改前） | 169.3 MB | 27.4 / 20.9 / 20.3 s | 13,313 文件 |
| DSH 单归档，同一份文件（改后） | 167.9 MB | 3.7 / 3.7 / 4.0 s | 606 文件 |

关键在这两行对比：它们装的是**同一份已经 prune 过的 12,708 个 DSH 文件**，安装包体积只差 1.4 MB（169.3 vs 167.9），唯一实质差别是目录树还是单个 tar。耗时差 5~7 倍，全部来自 12,708 次 CreateFile。DSH 带来的额外开销从 17~24 s 降到 0.6~0.9 s，落地文件数 13,313 → 606。

这也顺带回答了"prune 够不够"：不够。体积砍掉 67% 之后，目录树模式仍然要 20~27 s，因为剩下的文件还是得一个个创建。真正起作用的是把条目数从 12,708 降到 1。

顺带一提，安装包体积几乎没变。带 DSH 比不带 DSH 只大 31 MB（167.9 对 136.5）。156 MB 的裸 tar 进 NSIS 后被 solid LZMA 压掉了大半，压缩交给外层就够了，自己再包一层 gzip 只是白费 CPU。**收益全在安装耗时上，不在体积上**。这篇文章的标题原本叫"打包体积优化"，测量结束后真正的瓶颈一直是文件数，跟体积关系不大。

首次启动解压 4.5 s，期间界面正常可用。第二次启动 0.13 s，标记命中直接跳过。解压结果是 12,709 个文件 146.5 MB，与源树逐项一致，`runtime-manifest.json` 的 sha256 与 entry 都在位。

也就是说用户的等待从"安装时干等 20~27 s"变成了"安装 3.7 s + 首启后台 4.5 s"。后一段不挡路，软件已经能打开看照片了，只有 AI 面板第一次用要等几秒。

## 两个坑

**旧 exe 打进新安装包。** 首启解压的第一次验证中，60 秒后仍未生成缓存目录。排查结果指向安装包里的 `emulsion.exe`：时间戳还是前一天的，72.90 MB，并不包含新增的 `prepareDSHPayload`。原因是那次只执行了 `node build/package-windows-installer.mjs`，没有执行 `wails3 task build:windows`。`git status` 干净不代表产物新，改完 Go 源码必须重编再打包。重编后 exe 变成 59.60 MB（时间戳 2026/10/24 9:24:53），首启解压立刻变成 4.5 s。

**pack 任务没接线。** 上面提过，任务写了但没人调，构建全程无报错。这类"静默回退"比直接失败难查得多，因为两条路径都成功退出。所以 `package-windows-installer.mjs` 现在会在结尾打印本次走的是哪条路：

```
DSH payload: 1 file(s) inside the installer instead of the pruned tree's ~12.7k
```

看到这行才说明提速真的生效了。
