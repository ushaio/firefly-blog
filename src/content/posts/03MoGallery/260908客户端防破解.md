## 一、Wails 的架构决定了其逆向面

Wails = **Go 后端** + **Web 前端（HTML/JS/CSS）**

| 层面              | 逆向难度 | 说明                                                   |
| ----------------- | -------- | ------------------------------------------------------ |
| **前端资源**      | ⭐ 极低   | JS/HTML/CSS 本质是明文，从二进制中提取后几乎可直接阅读 |
| **Go 二进制**     | ⭐⭐ 较低  | Go 编译产物保留大量符号、类型、路径信息，反编译友好    |
| **前后端绑定**    | ⭐ 极低   | Wails 的 bindings 自动生成，接口名、参数结构一目了然   |
| **核心算法/密钥** | ⭐⭐ 较低  | 若硬编码在 Go 或 JS 中，均可被提取                     |

------

## 二、具体逆向途径

### 1. 前端资源提取（最容易）

Bash



```
# Wails 将前端资源嵌入二进制，但可通过工具提取
# 例如使用 binwalk、strings 或专用脚本提取嵌入的 zip/文件系统
strings myapp.exe | grep -i "function\|api\|key"
```

- 前端 JS 即使经过 webpack/vite 打包，也只是 **混淆** 而非加密
- 所有 API 调用路径、业务逻辑在前端完全暴露

### 2. Go 二进制分析

Bash



```
# Go 二进制默认保留完整符号表
go tool objdump myapp.exe
# 使用 Ghidra + Golang 插件可恢复函数名和结构体
# 使用 IDA Pro 的 GoReSym 插件可还原符号
```

- Go 的 runtime 信息、goroutine 调度等使逆向有迹可循
- `go build -ldflags="-s -w"` 只能去掉调试信息，**不能阻止逆向**

### 3. 运行时动态分析

- 使用 **Frida** hook Go 函数和 WebView 通信
- 使用浏览器 DevTools（Wails v2 在开发模式下可打开）审查前端
- 抓包分析前后端 IPC 通信

## 三、能做的加固措施（提高成本，非杜绝）

| 措施                                            | 效果                   | 局限                       |
| ----------------------------------------------- | ---------------------- | -------------------------- |
| **JS 混淆**（Jscrambler/javascript-obfuscator） | 增加前端分析时间       | 可被 deobfuscator 还原逻辑 |
| **Go 符号剥离** `-ldflags="-s -w"`              | 减小体积，去掉部分信息 | 对专业逆向者影响有限       |
| **Go 代码混淆**（garble）                       | 打乱函数名/变量名      | 控制流仍可分析             |
| **加壳**（VMProtect / Themida）                 | 增加静态分析难度       | 可被脱壳，且影响性能       |
| **关键逻辑移至服务端**                          | ✅ **最有效**           | 需要网络，增加架构复杂度   |
| **WASM 加密模块**                               | 增加提取难度           | 仍可被 dump 和分析         |
| **反调试 / 完整性校验**                         | 增加动态分析门槛       | 可被 patch 绕过            |

------

## 四、最佳实践建议

text



```
🔑 核心原则：不要信任客户端
```

1. **敏感逻辑放服务端**：许可证验证、核心算法、密钥管理 → 走 API
2. **前端只做 UI**：把 Wails 前端当作一个"厚壳浏览器"
3. **Go 端做中转**：前端 → Go binding → 加密请求 → 服务端
4. **使用 garble 编译**：`garble -literals -tiny build`
5. **运行时环境检测**：检测调试器、虚拟机、篡改
6. **代码签名 + 完整性校验**：防止二进制被 patch

------

## 五、结论

> **Wails 应用 ≠ 安全黑盒。**
>
> 它的 Web 前端天然透明，Go 后端逆向门槛也不高。如果你的威胁模型是"防止任何人逆向"，那 Wails（或任何客户端框架）都做不到。
>
> **正确的思路是：假设客户端一定会被破解，把安全边界放在服务端。**
