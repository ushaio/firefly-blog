目前主流的 Anthropic、OpenAI、Gemini 三家各有自己的对话协议：

- Anthropic：`/v1/messages`
- OpenAI：`/v1/chat/completions`、`/v1/responses`
- Gemini：`/v1beta/models/{m}:generateContent`

它们的分歧不在于"怎么传参数"，而在于**"谁拥有这次对话"**。这个判断决定了 harness 的架构复杂度、可移植性，以及你会不会被单一厂商锁定。全文围绕这条主线展开：先横向对照，再看受"状态归属"影响的请求体组织，最后落到适配层的工程做法。

> 术语约定：下文统一用 **block** 指代"最小可寻址单元"（IR 视角），具体到各厂商时再写回原名 `message` / `item` / `part`。

## 一、三家横向对照

| 维度        | Anthropic `/v1/messages`                     | OpenAI `/v1/chat/completions`       | OpenAI `/v1/responses`                                       | Gemini `/v1beta/models/{m}:generateContent`    |
| --------- | -------------------------------------------- | ----------------------------------- | ------------------------------------------------------------ | ---------------------------------------------- |
| 定位        | 面向 Agent 的原生接口                               | 事实标准，兼容面最广                          | Chat Completions 的继任者                                        | 长期 beta，靠厂商自行演进                                |
| 会话状态      | 无状态，全量重传                                     | 无状态，全量重传                            | 有 `previous_response_id` / Conversations                     | 无状态，但缓存是可 CRUD 的资源                             |
| 最小单位      | content **block** 数组                         | **message**（content 内再分 part）       | **item** 数组（消息与工具调用平级）                                       | **part** 数组                                    |
| 工具结果归属    | `tool_result` block 放进 **user 消息**           | 独立的 `role: "tool"` + `tool_call_id` | `function_call_output` 作为独立 item                             | **user 角色**的 `functionResponse` part           |
| 流式        | 细粒度事件（`message_start`/`content_block_delta`） | delta 式追加字段                         | 语义事件（`response.output_item.added`）                           | part 粒度增量                                      |
| 推理内容      | `thinking` block，必须回传且带 signature            | 协议不暴露                               | `reasoning` item + `reasoning.effort`                        | `thought` part + `thinkingBudget`              |
| 结构化输出     | `output_format` json_schema（早期靠 `tool_choice` 约束） | `response_format` + json_schema     | `text.format` json_schema                                    | `responseSchema` + `responseMimeType`          |
| 内建工具      | 无                                            | 无                                   | 有：web_search / file_search / code_interpreter / computer_use | 有：google_search / code_execution / url_context |
| 缓存哲学      | 请求体内 `cache_control` 断点                      | 自动前缀缓存                              | 自动前缀缓存                                                       | 独立资源 `cachedContents`                          |

两处需要补充：

- **system 的位置**不单列一行，因为它是"最小单位"的直接推论：Anthropic 顶层 `system` 字段、OpenAI 消息里的 `role:"system"`、Responses 顶层 `instructions`、Gemini 顶层 `systemInstruction`。真正的坑在"多段 system"（见三、1）。
- **内建工具与结构化输出**是两家"托管能力型"厂商（OpenAI Responses、Gemini）与 Anthropic 的分野，但这两项都属于"服务端替你做了一部分事"，与全文的"状态归属"主线同源，后面会回到它。

## 二、URI / 版本层面

**Anthropic 是"一个端点包打天下"。** `/v1/messages` 承担全部推理流量，`count_tokens`、`batches` 只是同一命名空间下的辅助端点。版本号不写在路径里，靠请求头 `anthropic-version` 加一组 `anthropic-beta` 开关做增量演进而非版本冻结——所以 v1 是一个长期演进的运行时，不是一份快照。

**OpenAI 有两条并行路线。** `/v1/chat/completions` 兼容面最广，几乎每个第三方模型、每个网关都先实现它；`/v1/responses` 是官方主推的新一代，语义更接近"一次 Agent turn 的完整输入输出"，把消息与工具调用平级成 item。截至 2026 年 10 月，官方给的是迁移指南而非弃用时间表，所以基础设施项目要同时维护两套适配器。

**Gemini 把版本写进路径**（`/v1beta`），方法名用 `:generateContent`、`:streamGenerateContent`、`:countTokens` 这类 Google AIP 风格的冒号方法，而非 RESTful 子资源。`v1beta` 意味着 surface 会增删改，工程上必须由适配层隔离——这层隔离不是可选项，是使用 `v1beta` 的前提。

## 三、请求体组织的差异（真正的痛点）

### 1. system 到底算不算一条消息

这是适配层最容易踩的地方。Anthropic 和 Gemini 把 system 提到顶层，OpenAI 用消息表示。看似只是搬家，影响却在**多段 system**：Anthropic 的 `system` 可以是 block 数组并挂 `cache_control` 断点，OpenAI 可以给多条 `role: "system"`，Gemini 的 `systemInstruction` 也能多 part。一旦跨层翻译，**"几段 system"常被压成一段，缓存断点也跟着丢**。

这条是后文第五节"IR 归一"最直接的论据：IR 里必须把 system 建模为**有序 block 列表**而非字符串，否则任何一次翻译都是单向损失。

### 2. 工具调用结果的归属

三家差异最大、最容易写错的一处：

- **Chat Completions**：assistant 带 `tool_calls` → 下一条 `role: "tool"` + `tool_call_id`，结果是独立消息。
- **Anthropic**：`tool_use` 是 assistant 消息里的一个 block → 结果以 `tool_result` block 放在下一条 **user** 消息里，靠 `tool_use_id` 关联，且 `tool_use` 后必须紧跟对应 `tool_result`，不配对直接 400。
- **Gemini**：`functionCall` 是 model 返回 parts 里的一个 part → 结果用 **user 角色**的 `functionResponse` part 回传。早期版本靠 `functionCall.name` 关联（并行调用时靠名称与顺序消歧），`id` 是后来才补齐的。

同一次工具调用，三种协议里的形状：

```
Chat Completions:  assistant{tool_calls:[{id:"c1",…}]}  →  tool{tool_call_id:"c1", content:"…"}
Anthropic:         assistant{[text, tool_use{id:"u1"}]} →  user{[tool_result{tool_use_id:"u1"}]}
Gemini:            model{[functionCall{name,args}]}     →  user{[functionResponse{name,response}]}
```

同一个 workflow 在三种协议里落地成三种不同的消息图谱。"OpenAI 兼容层"看着简单，真要端到端支持工具循环，做的是**状态机对齐**而不是字段映射。

### 3. 流式增量怎么切

因为最小单位不同（message / block / part），流式增量的切分维度也就不同。Anthropic 要处理"一个 content block 开始 / 若干 delta / block 结束"，Gemini 按 part 推增量，Chat Completions 则是在平坦的 delta 字段上做累积。

写统一渲染器时的做法：**以 block 为统一最小粒度**，把 part 增量与 delta 累积都先归一成 block 事件流（`block_start` / `block_delta` / `block_stop`），再交给渲染层。三种节奏在归一之后才会变成同一种。

### 4. 推理内容能不能回传

Anthropic 的 `thinking` block 在下一轮必须原样带回（含 signature），且**含 `tool_use` 的轮次强制要求回传**，否则请求被拒；Gemini 的 `thought` 类似。Chat Completions 协议本身没有这一层概念——个别厂商在兼容层加了 `reasoning_content` 这类扩展字段，但不在规范内。所以**任何经过 Chat Completions 格式中转的链路都会丢推理上下文**，这是不少自建网关的通病。Responses 则用 `encrypted_content` 显式支持回传。

## 四、会话状态归属：这是分水岭

Chat Completions 和 Messages 都是**无状态**协议：每轮重传完整历史，服务端不认"你在继续聊"。上下文管理完全落在客户端——截断、摘要、压缩、检索召回都是 harness 自己干的事。

Responses 把一部分状态搬到服务端（`previous_response_id`、Conversations、`store`），甚至能在服务端托管工具执行与文件。好处是省带宽、可复用 reasoning item、内建工具即开即用；成本是状态绑在厂商侧，成本与隐私的黑盒变深，且迁移时要为"服务端那部分历史"另做导出。

Gemini 走中间路线：主体无状态，但把 `cachedContents` 做成可 CRUD 的一等资源，缓存不再藏在请求体的标记位里。

## 五、对 Agent / Harness 的落地影响

1. **适配层要做语义转换，不是字段重命名。** 内部定义一套 IR，把 message / block / item 三种模型先归一（选 block 模型，表达力最强），再分发到各 provider。system 在 IR 里必须是有序 block 列表，工具调用必须有独立的状态机节点。
2. **工具循环必须写成状态机。** 每个 provider 对"`tool_use` 之后必须出现什么"的约束不同，出错要能识别并修正，而不是盲目重试。补救时**插一个明确的失败/取消 `tool_result`（标记 error），不要伪造成功**——如果工具已产生副作用，伪造成功会让模型基于错误的世界状态继续推理。
3. **推理内容单独建通道。** 在 IR 里保留 reasoning block，并用一个 opaque 字段承载厂商加密串；对不支持的目标显式降级，而不是静默丢弃。
4. **缓存按 provider 分别建模。** 断点式、自动前缀式、资源式三种策略，一个"打开缓存"开关糊不过去，否则命中率会静默归零。建议在 IR 里用 `cache_binding` 这类结构性描述（锚点位置 / TTL / 资源 id），而非布尔位。
5. **错误语义要收敛。** 各家错误体结构、错误码、幂等性、`request_id` 追踪都不同，得在适配器里统一成错误分类，上层才能做正确的退避。

## 六、一个观察

三家协议的分歧，本质上是**"谁拥有这次对话"**：

- **Anthropic** 明确表态对话归客户端，服务端只做无状态推理，所以把表达力做得很足（block、cache 断点、thinking 全回传）。
- **OpenAI** 在 Chat Completions 上继承了同样姿态，但用 Responses 开始往服务端收——托管工具、会话指针、可复用 reasoning item 都是"收"的迹象。
- **Gemini** 是 Google 一贯的"资源 + 方法"世界观，缓存、文件、批量都做成一等资源。

所以写 harness 时最先该定的不是"支持哪几家"，而是"状态归属选哪一边"。给一个可操作的判据：

- **要换厂商、要可控** → 客户端持有。适配层复杂，但真相始终在本地。
- **卖的是省心与长上下文** → 服务端持有。短期最省事，但要接受厂商锁定。
- **两者都要** → 把服务端状态当作**可丢弃的加速层**：客户端始终保有全量真相，服务端丢了也不影响正确性。

前两条是架构选型，第三条是大多数产品真正该走的路。
