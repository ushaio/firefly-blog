# 本地资源库索引优化方案：从库文件分层到 FTS5 定向维护

本地资源库的索引要解决的是一个老问题：磁盘上有一堆照片，散在各级文件夹里，程序得知道每一张的内容、位置和拍摄时间，还要能按关键词搜出来、按时间或大小排序翻页。

这个索引同时被三种压力拉扯。写入要快，否则首次建库和后续增删都难受；查询要快，关键词和深翻页都不能随数据量退化；已有的索引重复走一遍还得便宜，否则每次扫描都在做无用功。

Emulsion Desktop 的本地库把这几块拆成七个相对独立的决定：库文件怎么分、扫描怎么比、FTS 索引怎么维护、查询怎么拼、写入怎么批、缩略图怎么记账、改动怎么监听。下面按代码里实际的层次讲这套方案是怎么落地的。

## 库文件分层：元数据与缓存分开存

本地库有两个 SQLite 文件。

`library.db` 存资产、文件夹、EXIF、标签、相册、人脸、向量这些元数据，是真正不可丢的索引。`derivatives.db` 存缩略图和预览的记账，属于纯缓存，删了顶多重画一遍。

拆开的收益很直接（见 `local_library/store_derivatives.go` 顶部注释）：

- 缩略图 worker 不再和扫描器抢 `library.db` 的唯一写连接，批量索引期间写锁归扫描器独占。
- 缓存库可以开 `synchronous=OFF`，因为每一行都能从源文件重建，写坏一行的代价只是重画一张缩略图。
- `library.db` 保持小体积，在线备份和 `PRAGMA quick_check` 在大库上才跑得动。

后两条在库体量变大之后很实际。缓存数据是每张图一行的量级，把它塞进主库，备份体积和完整性检查时间会被一起拖大。

## 扫描走整库内存 diff

旧的初始化写法是逐文件一套 `BEGIN IMMEDIATE ... COMMIT`。单写连接下，每个文件一次 WAL 提交，哪怕这个文件什么都没变，也要付一次事务的代价。文件一多，这条路径就是纯线性的开销堆叠。

现在的扫描管线在 `local_library/scan_pipeline.go` 顶部写成四步：

1. 一次目录遍历，收齐路径、大小、修改时间。`entry.Info()` 直接复用操作系统已经返回的目录项，不再额外 `stat` 一次。
2. 把现有索引整库读进内存，在内存里做 diff。
3. 只有变化的文件进入并行 inspect（解码头、读 EXIF、探测 Live Photo），由一个写者批量提交。
4. 索引对齐之后再进入缩略图预热，这一步可以交给后台。

第 2 步是整套方案的核心。`indexSnapshot` 一次顺序全表读把资产读成 `map[path_key]assetIndexRow`，`folderSnapshot` 同理把文件夹读进来。然后 `classifyScanEntries` 拿目录树和这份快照做纯内存比对，大小和 mtime 都对得上的文件直接判为未变，写入次数为零。

带来的直接结果是：对已经索引过的库，一次扫描的写入成本为零，主体只剩一次顺序读；冷库首次没有快照可用，成本落在真正的 inspect 和写入上，这部分省不掉，只能靠批量摊薄。

第 3 步的并行度是 `max(2, min(GOMAXPROCS, 8))`，批量大小 `indexWriteBatchSize = 256`。首批在攒够 32 条或过一个 250ms 的 tick 就先落地，后面按 256 条一批提交。首批先落地是为了让界面早点看到东西，256 这个值则是提交开销和进度响应之间的折中。

文件夹祖先的解析也做了缓存。`ensureFolders` 在一个事务里按相对路径逐级建父目录，路径段走内存 `cache`，所以五万个文件散在五百个文件夹里，实际查库次数是五百量级。

## FTS5 索引改成 rowid 定向维护

FTS5 这块是老问题最集中的地方，`local_library/store_search.go` 开头把来龙去脉写得很清楚。

旧版的 `asset_search` 表里有一列 `UNINDEXED asset_id`，靠触发器维护，逻辑是 `DELETE FROM asset_search WHERE asset_id=?` 再重新插入。问题是 UNINDEXED 列没有索引，每次删除都得扫整个索引。索引 N 个资产，总代价是 O(N²)。

现在的做法换了键。`asset_search` 直接用 `assets.local_id` 当 FTS 的 rowid：

```sql
CREATE VIRTUAL TABLE IF NOT EXISTS asset_search USING fts5(
    file_name, relative_path, display_title, notes, tags, collections, camera,
    tokenize='unicode61'
)
```

维护就变成 rowid 查找。更关键的是触发器完全不碰索引本体了，它们只往 `asset_search_dirty` 这张队列表里追加脏行：

```sql
CREATE TRIGGER IF NOT EXISTS asset_search_assets_insert AFTER INSERT ON assets BEGIN
    INSERT INTO asset_search_dirty(asset_id)
    SELECT NEW.id WHERE NOT EXISTS (SELECT 1 FROM asset_search_dirty dirty WHERE dirty.asset_id=NEW.id);
END
```

真正的重建在 `flushAssetSearch`，用 set-based 的 `DELETE ... WHERE rowid IN (...)` 加 `INSERT ... SELECT` 一批换掉。批量索引因此是每批一次合并写，而不是每行一次昂贵重建。

这段代码里还有个容易被忽略的坑，注释专门记了：触发器写在 `INSERT OR IGNORE` 上会炸 `UNIQUE constraint failed`。因为外层 UPSERT 自带 `ON CONFLICT` 子句，SQLite 规定触发器跟随外层语句的冲突策略，其他约束就走默认的 ABORT。所以触发器体改成自己写 `WHERE NOT EXISTS` 守卫，不依赖冲突子句。

## 查询侧的子查询与游标分页

关键词过滤在拼 `where` 时是一条子查询：

```sql
a.local_id IN (SELECT rowid FROM asset_search WHERE asset_search MATCH ?)
```

旧写法是对每个候选资产行重算一次 `MATCH` 的 correlated EXISTS，行数一多就是重复劳动。改成子查询后整条查询只做一次 FTS 匹配。

分页用 keyset 游标，不用 OFFSET。排序表达式同时进游标比较和 `SELECT` 列，深翻页不会越翻越慢。单页上限 200。count 查询和主查询共用同一份 `where`，避免两处拼接漂移。

## 写入批量与 SQLite 调优

`openStoreWithMigration` 里的 DSN 是一组针对大库批量导入的 pragma：

```
journal_mode(WAL)
synchronous(NORMAL)
cache_size(-32768)
temp_store(2)
wal_autocheckpoint(4000)
busy_timeout(10000)
foreign_keys(1)
txlock=immediate
```

`cache_size` 取负值是按 KiB 表达，这里是 32 MiB 页缓存，让资产和文件夹的 B 树在索引期间常驻内存。`temp_store=2` 是 MEMORY，排序和 FTS 合并的临时结构不落盘。`wal_autocheckpoint=4000` 把 checkpoint 间隔拉长，避免批量导入时每几百页就回写一次。`_txlock=immediate` 让事务一开就拿到 WAL 写预留，躲开延迟事务先读旧快照、再被缩略图 worker 抢先提交后撞上的 `SQLITE_BUSY_SNAPSHOT`。

连接数固定为 1。modernc 驱动的页缓存状态是连接级的，同时开多个连接访问同一个大 WAL 库，在 Windows 上会冒出误导性的 `SQLITE_CANTOPEN`。

批量 API 是一整套，不是零散几处：`writeIndexedFiles`、`setPreviewResults`、`updateLivePhotos`、`markAssetsMissing`、`stampScanToken`、`reactivateAssets`、`derivativeStore.setResults` 全部单事务批处理。绑定参数用 `chunkedAssetIDs` 压到 500 以内，避开 `SQLITE_MAX_VARIABLE_NUMBER`。

覆盖度上，建库脚本里有 22 条显式 `CREATE INDEX`（`library.db` 21 条，`derivatives.db` 1 条），全部带 `IF NOT EXISTS`，跟着 `migrate()` 每次开库幂等执行。按用途分组：

**资产列表的主查询路径**，都是「可用性 + 排序键 + id」的复合索引，和 `listAssets` 的几种排序对应：

- `idx_assets_availability_discovered (availability, discovered_at DESC, id DESC)`
- `idx_assets_modified (availability, modified_at_ns DESC, id DESC)`
- `idx_assets_rating (availability, rating DESC, id DESC)`
- `idx_assets_favorite (availability, is_favorite, discovered_at DESC)`
- `idx_assets_folder_name (folder_id, file_name COLLATE NOCASE, id)`

**FTS 的挂载点**：

- `idx_assets_local_id ON assets(local_id)`，唯一索引，`asset_search` 的 rowid 就靠它对齐

**关联表与子表**（外键反查与过滤用）：

- `idx_asset_tags_tag_asset (tag_id, asset_id)`
- `idx_collection_assets_asset_collection (asset_id, collection_id)`
- `idx_asset_live_photos_live (is_live_photo, asset_id)`
- `idx_asset_clips_asset (asset_id, start_ms)`
- `idx_asset_derivations_source (source_asset_id, created_at DESC)`

**文件夹与相册树的层级遍历**：

- `idx_folders_parent (parent_id, name COLLATE NOCASE)`
- `idx_collection_groups_parent_position (parent_id, position, name COLLATE NOCASE)`
- `idx_collections_group_position (group_id, position, name COLLATE NOCASE)`

**人脸与向量**（按模型空间过滤）：

- `idx_asset_faces_asset (asset_id, model_id, model_version)`
- `idx_asset_faces_model (model_id, model_version, quality)`
- `idx_person_groups_model (model_id, model_version, state)`
- `idx_asset_embeddings_model (model_id, model_version, dim)`
- `idx_asset_embedding_status_model (model_id, model_version, status)`

**云同步状态**（`M009`/`M010` 迁移里单独建，不在主 schema 数组里）：

- `idx_assets_cloud_photo (cloud_photo_id)`
- `idx_assets_cloud_source (cloud_storage_source_id)`

**缓存库**：

- `idx_asset_derivatives_variant_accessed (variant, status, last_accessed_at)`，`trimPreviewCache` 的 LRU 裁剪和 `previewDerivativeEntries` 的排序都走它

另有一批不写成 `CREATE INDEX` 的索引：`assets.id`、`assets.path_key` 上的 `UNIQUE` 约束，`tags.name_key` 的 `UNIQUE`，以及各关联表的复合主键，SQLite 都会自动建隐式索引（`sqlite_autoindex_*`）。`asset_search` 是 FTS5 虚拟表，它的倒排索引和 shadow 表由 FTS5 自己维护，也不在这份清单里。

## 缩略图记账独立成库

缩略图这一段同样绕开了"每张图一次往返"。

批量预热按 `thumbnailPrefetchBatch = 500` 一次预取资产行，worker 池并发生成。记账走合并写，只有用户当前可见的交互请求才即时 flush。旧缓存文件只删被新 key 取代的那一个，不再 glob 整个目录（旧实现每生成一张就扫一次目录，是另一处 O(N²)）。预览缓存按 `last_accessed` LRU 裁到 2GB 上限。

因为 `derivatives.db` 是独立文件，这整段的写入压力都不落在 `library.db` 的写锁上。

## 增量监听按路径 reconcile

日常增删几个文件不该触发整库遍历。`fsnotify` 递归注册目录，事件做 700ms 去抖后按路径增量 `reconcilePath`。只有目录级事件、或者删除/改名后已经 stat 不到的路径，才回退到全扫。

`reconcilePath` 复用和扫描同一条管线，所以监听器改一个文件，走的也是"先比大小 mtime，未变就直接返回"这套判断。增量路径和全量扫描共用同一套判定，是这套方案能同时覆盖两种场景的前提。

## 方案小结

上面几节各自只解决一段，合起来是同一个取舍：把按文件计的开销，摊成按批计。

1. **未变文件零写入**。整库 diff 在内存完成，重复扫描的主体只剩一次顺序读。
2. **FTS 从 O(N²) 变 rowid 维护**。脏队列加 set-based 重建，批量索引每批一次合并写。
3. **查询一条 FTS 子查询加 keyset 游标**。关键词与深翻页不随数据量二次放大。
4. **库文件分层**。缓存写入不抢主库写锁，备份和完整性检查保持轻量。
5. **批量写入与 pragma**。提交摊薄、页缓存常驻、临时结构不进磁盘。
6. **缩略图记账独立成库**。记账合并且有容量上限，不占主库写锁。
7. **增量监听**。日常改动不触发全量遍历，且与全量扫描共用同一套判定。

## 方案目前的边界

代码和文档里都标了没覆盖的部分，记一下，免得看上面以为已经封顶。

- **前端还在整查询 drain**。`LocalLibraryWorkbench.tsx` 现在是 `while (result.nextCursor)` 一页页把整个查询拉完，文档把"改成按需加载"列为独立待办。结果集大时，首屏之后的持续拉取仍然占着后端。
- **非 JPEG 的元数据 inspect 偏贵**。这部分还留在初始化流程里，优化它们是另一项工作。
- **语义检索是暴力 KNN**。`embeddingSearchSemanticRank` 读该向量空间的全部向量逐一算余弦，O(N) 一次查询，靠 `embeddingSearchRankWindow = 200` 截断排名窗口，再和 FTS 的 bm25 排名用 RRF（常数 60）融合。库里开了 embedding 之后，这一路是实际成本。关键词通道走 FTS5 不受影响。

这套索引的本体是把"每文件一次往返"换成"整库一次 diff 加批量提交"，再给 FTS 换一把能定向维护的钥匙。剩下的边界，都在前端取数和向量检索那两头。

## 额外补充：几万张照片时，怎么让它别卡在开库那一下

前面讲的是方案本身。这一节换个视角，从"打开一个几万张照片的库"这个具体场景回看上面那些决定各自挡在哪。

**首次建库（冷库）**。这时候没有快照可比，每张照片都要真的打开读一遍，文件头、EXIF、Live Photo 探测一样都省不掉。成本落在 inspect 和写入上，只能靠两处摊薄：inspect 用 worker 池并行，写入按 256 条一批提交。进度条靠首批 32 条或 250ms 的 tick 先动起来，用户不用盯着一个静止的界面等。

**再次开库（热库）**。这是差别最大的一步。整库 diff 在内存里跑完，大小和 mtime 都对的照片一条都不写。剩下的主体工作只有一次顺序全表读，把索引拉进内存。文件数从两万涨到十万，这一段的耗时涨得很慢。

**开库之后立刻能看到什么**。索引对齐完就解锁文件夹操作，缩略图预热接着跑，可以交给后台。也就是说"能浏览"和"缩略图全画完"被解耦了，不必等所有缩略图都生成才让用户进门。

**卡顿最容易藏在哪**。三个地方值得盯：FTS 维护如果还是旧的 UNINDEXED 删法，索引到几万条就是 O(N²)，开库会随库变大显著变慢；缩略图记账如果每张图一次提交又每张扫一遍目录，预热阶段是另一处 O(N²)；前端如果一页页把整个查询 drain 完，库越大首屏之后的持续拉取越重。前两个已经在方案里改掉了，第三个还留着，见上一节。

**几个数量级的感觉**。五万个文件散在五百个文件夹里，文件夹解析的查库次数是五百量级；未变文件的写入次数是零；关键词查询整条只做一次 FTS 匹配，旧的写法是每行一次；深翻页走游标，页码翻到几百页也不变慢。

开库慢的根源是每个文件都要单独走一遍数据库。把它换成整库比一次，再按批提交只写变化的部分，卡顿的那一下就被摊平了。
