# 局部重绘：模型不肯吃蒙版，我们就自己裁一块贴回去

Emulsion Desktop 的 AI 生图页里有个「局部重绘」档：涂一块，让模型只重画那一块。

局部重绘听起来像个绘制功能，实际做下来是三件互相牵制的事叠在一起。第一版我们老老实实按 provider 的 mask 协议做，结果接连踩坑：蒙版尺寸对不上被打回、涂完又擦掉的蒙版照样发出去白烧配额、百炼那边的极性还是反的。等把「必须让模型支持 mask 协议」这条前提掀掉之后，反而豁然开朗，干脆不把蒙版发出去，客户端自己裁一块、改一块、贴回去。

下面按当时排查和改造的顺序记一遍。

---

## 先看症状：四种失败长得很像，根因完全不同

这一段是踩坑的原始现场，后面几节都是从这里拆出去的：

1. **`mask 与 image 尺寸不符`**。蒙版是按显示画布渲的，底图是原图，两边差了一个缩放系数。
2. **涂抹完全没反应，配额照扣**。用户涂了一片又整片擦掉，笔迹还在，但蒙版已经是全不透明，provider 认为「什么都不用改」。
3. **403 `AccessDenied ... does not support asynchronous calls`**。百炼这个报错长得像「密钥没权限」，实际是选了一个不吃 mask 的模型。
4. **`The height/width of the image should be between 512 and 4096 pixels`**。单反直出的照片原样直传，两边像素都超了。

前两个在渲染进程，后两个在协议层。我们先从前两个修起。

## 蒙版为什么不能存像素坐标

同一片涂抹要落在两种尺寸上：编辑器里受窗口限制的显示画布（缩略图大小），和真正发给 provider、必须与底图逐像素同尺寸的蒙版。如果笔迹存的是像素坐标，显示层缩一次就再也对不回原图了。

所以 `frontend/src/lib/photo-repaint/mask.ts` 里的笔迹一律存归一化坐标：

```ts
export interface MaskStroke {
  /** 归一化坐标（0-1），相对参考图的宽高。 */
  points: MaskPoint[]
  /** 笔宽，同样按参考图**宽度**归一化；导出时乘目标宽度还原成像素。 */
  width: number
  /** 橡皮擦：把已经涂上的区域恢复成「保留」。 */
  erase: boolean
}
```

笔宽按**宽度**归一化而不是长边，是为了窄长图上的笔迹不被拉成椭圆。几档参数：笔宽限制在 `MASK_MIN_STROKE_WIDTH = 0.01` 到 `MASK_MAX_STROKE_WIDTH = 0.25`，默认 `0.06`。

还有一个不起眼但必要的抽稀。一次拖动能在 `points` 里塞进上千个点，所以两点距离小于 `MASK_MIN_POINT_DISTANCE = 0.0015` 就把后一个丢掉：

```ts
export function appendMaskPoint(stroke: MaskStroke, x: number, y: number): boolean {
  const last = stroke.points[stroke.points.length - 1]
  if (last && Math.hypot(x - last.x, y - last.y) < MASK_MIN_POINT_DISTANCE) return false
  stroke.points.push({ x, y })
  return true
}
```

函数返回「是否真的接上了」，调用方据此决定要不要重绘。原地微抖时不必重画整张画布。这里刻意直接改 `stroke` 对象（它在 canvas 事件里以 ref 形式存在），避免每次 `pointermove` 都触发一次 React 渲染。

## 一份笔迹，两套配色

蒙版协议约定的是「**透明**的像素才是要重绘的区域」，而人在屏幕上涂抹时想的是「涂到的地方要重画」。这两件事是反的。

导出时先铺满不透明底（等于全部保留），再用 `destination-out` 把涂过的地方抠成透明：

```ts
ctx.fillStyle = '#ffffff'
ctx.fillRect(0, 0, ctx.canvas.width, ctx.canvas.height)
drawMaskStrokes(ctx, ctx.canvas.width, ctx.canvas.height, strokes, 'mask')
```

预览和导出共用同一个 `drawMaskStrokes`，只换 `MaskDrawMode`（`'mask' | 'preview'`）。所以内层只有一行判别：

```ts
const punchThrough = mode === 'mask' ? !stroke.erase : stroke.erase
ctx.globalCompositeOperation = punchThrough ? 'destination-out' : 'source-over'
ctx.strokeStyle = mode === 'mask' ? '#ffffff' : MASK_PREVIEW_COLOR
```

顺序也有讲究。橡皮只擦掉它**之前**涂上的区域，所以必须一笔一笔按数组顺序画，不能按 `erase` 分组。单击（没有拖动）时单独画一个圆点，否则用户点一下得不到任何反馈。

`MASK_PREVIEW_COLOR = 'rgba(56, 189, 248, 0.55)'` 这枚高亮色本来藏在模块里，后来提到导出，是为了让「编辑时的涂抹预览」和「记录详情里的重绘区域回看」用同一个颜色语言。同一片区域在两处是同一个颜色，用户不用重新认一遍。

## 「涂了又全擦掉」的蒙版，不能让它发出去

对应症状里的第二条。这里有个想当然的写法是数一数笔迹有没有东西：

```ts
// 错的：先涂一片再整片擦掉，笔迹还在，蒙版已经全不透明
strokes.length > 0
```

正确做法是真的扫一遍 alpha。`maskHasInpaintArea` 把笔迹缩到长边不超过 `MASK_PROBE_MAX_EDGE = 256` 的小画布上，逐像素看：

```ts
const scale = Math.min(1, MASK_PROBE_MAX_EDGE / Math.max(width, height))
// ... 铺白底 + 画笔迹，然后
for (let index = 3; index < data.length; index += 4) {
  if (data[index] < 200) return true
}
```

4096² 的原图按原分辨率扫要 64MB 的 ImageData，缩到 256 的探针上只要几万像素，成本可以忽略。扫不到可重绘区域时，「确定」按钮直接禁用，一次请求都不会发出去。

## 涂抹时不能触发 React 渲染

`frontend/src/features/design-studio/MaskEditorDialog.tsx` 是一个 portal 弹窗：画笔、橡皮、笔宽滑杆、撤销、清空、Esc 关闭。

显示画布首选 `DISPLAY_MAX_WIDTH = 620` × `DISPLAY_MAX_HEIGHT = 420`，还会被容器再压一次。所以坐标换算一律走 `getBoundingClientRect()`，不做任何尺寸假设：

```ts
const rect = canvas.getBoundingClientRect()
const x = (event.clientX - rect.left) / rect.width
const y = (event.clientY - rect.top) / rect.height
return { x: Math.min(1, Math.max(0, x)), y: Math.min(1, Math.max(0, y)) }
```

进行中的那一笔存在 `activeStrokeRef` 里，靠 rAF 合并重绘，只有 `pointerup` 才把整笔提交进 state。否则一次拖动会让整页跟着渲染几十次。背板按 `Math.min(2, devicePixelRatio)` 放大，笔迹才不会糊。

### 那次画布一片空白，问题出在一句守卫

改造过程中有个现象值得单独记：蒙版编辑器打开后，画布**完全是透明的**，涂了也看不见，但「确定」按钮亮了、撤销也可用。

这意味着涂抹其实一直在正常进 state，只是从没被画出来。而容器被 `aspect-ratio` 撑得尺寸完全正常。

最后定位到「按帧合并重绘」的守卫。它最初写成「`frameRef.current` 非零就直接 return」，而卸载清理只 `cancelAnimationFrame`、**没有把句柄归零**。开发环境 StrictMode 的双次挂载正好踩中：第一次挂载排下的那一帧被 cleanup 取消，句柄却留在非零值上，重新挂载后之后每一次 `scheduleRender()` 都被同一个守卫挡下，`render()` 一次都没跑。

修法是两边对称：

```ts
const scheduleRender = useCallback(() => {
  if (frameRef.current) window.cancelAnimationFrame(frameRef.current)
  frameRef.current = window.requestAnimationFrame(() => {
    frameRef.current = 0
    render()
  })
}, [render])

useEffect(() => () => {
  if (frameRef.current) {
    window.cancelAnimationFrame(frameRef.current)
    frameRef.current = 0   // 取消后必须归零
  }
}, [])
```

教训很朴素：把 rAF 句柄存进组件级 `ref` 时，「取消」必须连「归零」一起做，否则那句守卫会永久为真。而且它是「不画」而不是「不工作」，所以现场看起来像「图没显示、也没法涂」，排查方向很容易跑偏到样式上去。

## 导出尺寸在页面侧再确认一次

蒙版编辑器点「确定」后，页面把笔迹渲成 PNG，并且再断言一次尺寸：

```ts
const rendered = renderMaskDataUrl(targetSize.width, targetSize.height, next)
if (rendered.width !== targetSize.width || rendered.height !== targetSize.height) {
  setMask(null)
  toast.error('蒙版尺寸与目标图不一致，请重新涂抹')
  return
}
```

显示画布、缩略图、底图原始尺寸三者一旦有人搞混，provider 只会回一句「mask 与 image 尺寸不符」，错误信息离现场很远。

这里有个细节：`targetSize` 来自 `loadImageSize(target.dataUrl)`，也就是 data URL 解码后的**真实像素**，不是 `asset.width / asset.height`。因为 `readRepaintReference` 会把大图缩放后重编码，库里记的尺寸这时候已经和实际发出去的字节不符了。

面板上还有一张 80px 的 `MaskThumbnail`：底图加当前笔迹，按图片自身比例 contain 缩进小方框。缩略图哪怕被拉伸一点点，用户也会以为涂抹位置偏了。

它的一个特殊分支是回显。从「我的作品 → AI图片」点「修改」回来时，记录里只有蒙版 PNG、没有笔迹，此时要把蒙版按同一套预览配色叠上去，否则文案写着「已回显重绘区域」、图里却空无一物。

## 参考图先收进 512 到 4096

`frontend/src/lib/photo-repaint/client.ts` 负责把库里的照片读成可直传的 data URL。除了体积和格式，还要保证两边像素落进 `[512, 4096]`，这跟百炼万相图像编辑对 `base_image_url` / `mask_image_url` 的硬约束一致。OpenAI 兼容的 `/images/edits` 对尺寸宽松，落在区间内对它无害。

常量都放在纯逻辑层 `photo-repaint/core.ts`（不 import React、DOM、Wails，单测能直接 bundle）：

- `REPAINT_REFERENCE_MAX_BYTES` 8 MiB，超过就先经画布重编码，不把几十 MB 原图塞进 multipart
- `REPAINT_REFERENCE_MAX_EDGE` 1536，体积/格式驱动的重编码长边上限
- `REPAINT_SOURCE_MIN_EDGE` 512、`REPAINT_SOURCE_MAX_EDGE` 4096，与百炼硬约束对齐
- `REPAINT_ACCEPTED_REFERENCE_MIMES` 只认 png / jpeg / jpg / webp
- `REPAINT_PROMPT_MAX_LENGTH` 8000，与 Go 侧 `maxRepaintPromptLength` 对齐

缩放系数是一个纯函数，只缩不放大超限的长边；只有当放大后长边仍不越界时，才为短边不足 512 的图放大：

```ts
export function repaintSourceScale(width: number, height: number): number {
  const maxEdge = Math.max(width, height)
  const minEdge = Math.min(width, height)
  let scale = 1
  if (maxEdge > REPAINT_SOURCE_MAX_EDGE) scale = REPAINT_SOURCE_MAX_EDGE / maxEdge
  if (minEdge * scale < REPAINT_SOURCE_MIN_EDGE) {
    const needed = REPAINT_SOURCE_MIN_EDGE / minEdge
    if (maxEdge * needed <= REPAINT_SOURCE_MAX_EDGE) scale = needed
  }
  return scale
}
```

极端长宽比（超过 8:1）两边不可兼得，此时保留长边缩放系数，短边交给上游报错。这种图本来也不该整张送去重绘。

重编码格式按源图选：JPEG / WebP 照片编成 JPEG（质量 0.92），避免 4096px 照片编成 PNG 后膨胀到几十 MB；PNG 与其余格式（HEIC / AVIF / GIF 经解码后）保持 PNG，不丢透明通道。

还有个容易写反的顺序问题。`readRepaintReference` 是**先解码、再决定缩放**：`repaintReferencePlan(mimeType, byteSize)` 只看格式与体积，真正的 `repaintSourceScale` 需要 `naturalWidth / naturalHeight`，所以 blob 一定要先 `createObjectURL` → `new Image()` 解码，等 `drawImage` 之前才 revoke。像素已经进内存了，URL 失效不影响后续绘制。

## 第一版：把蒙版直接发给 provider

这条是原始方案，也是云端通道唯一能走的路。

请求从渲染进程发到本地 `POST http://127.0.0.1:{port}/ai/generate`，体里带 `mask`：

```ts
body: JSON.stringify({
  conversationId: conversation.id,
  generateImage: true,
  prompt: params.prompt,
  userPrompt: params.prompt,
  imageModel: params.imageModel,
  imageSize: params.imageSize,
  images: images.length ? images : undefined,   // 顺序即语义：目标图必须第一张
  mask: params.maskDataUrl,
})
```

响应是 SSE，只有三种事件：`status`（进度文案）、`error`、`done`（带 `messageId`）。拿到 `messageId` 之后再调 `GetAiImageDataURL(messageId)` 取最终图片。

解析器 `consumeRepaintStream` 写成了纯函数，逐块消费文本、自己维护半个帧的 `buffer`，所以跨块断帧、未知事件、错误帧都能被单测覆盖。

进入 provider 之前，`handleImageGeneration` 先把「蒙版必须配且只配一张图」拦下来：

```go
mask := strings.TrimSpace(input.Mask)
if mask != "" && len(input.Images) != 1 {
	return errors.New("局部重绘需要且只需要一张参考图")
}
```

`normalizeImageSize` 只认三档（`1024x1024`、`1024x1792`、`1792x1024`），其余一律回落 `1024x1024`。

### 协议层只留一张登记表

`services/editor-ai-image.go` 里只放三样东西：分派、两家共用的辅助、以及新增一类供应商时唯一要动的登记表。

```go
type imageGenerationProvider func(provider config.AIProviderConfig, prompt, model, size string, sourceImages []string, mask string, onStatus func(string)) ([]byte, string, string, error)

var imageGenerationProviders = map[string]imageGenerationProvider{
	config.AIProviderTypeOpenAI:    generateImageOpenAI,
	config.AIProviderTypeDashScope: generateImageDashScope,
}
```

查不到时回落到兼容 OpenAI 的实现，与 `config.NormalizeAIProviderType` 的兜底一致。加一家的成本就是：新写一个文件，在表里登记一行。

`maxRepaintMaskBytes = 4 << 20` 也放在共用文件里。OpenAI 兼容端点在 `/images/edits` 上普遍把 mask 限制在 4MB，百炼那边也吃不下更大的图，两家共用同一档上限。

### 兼容 OpenAI：multipart 和两条硬校验

`editor-ai-image-openai.go` 的入口逻辑是「有参考图就去改图，没有才文生图」。改图走 `POST {baseURL}/images/edits` 的 multipart：参考图逐张作为文件字段（多张时 `image[]`，超过 16 张直接报错，不浪费一次上传），蒙版单独一个 `mask` 字段。

针对蒙版有两条校验，都是踩过之后补的：

```go
if maskMime != "image/png" {
	return nil, "", "", fmt.Errorf("蒙版必须是 PNG（透明区域为需要重绘的部分），当前为 %s", maskMime)
}
if len(maskData) > maxRepaintMaskBytes {
	return nil, "", "", fmt.Errorf("蒙版超过 %dMB，请减少涂抹范围", maxRepaintMaskBytes>>20)
}
```

### 百炼：三个分叉

`editor-ai-image-dashscope.go` 里的差异最多，值得单独列。

**一、路由形状不同。** 千问图像系列在兼容模式下把文生图与图生图合并在 `POST {BaseURL}/images/generations`，靠「带不带 `image` 字段」区分，**没有** `/images/edits`，也不接受 mask。尺寸只能取它自己那几档（`1328x1328` / `928x1664` / `1664x928`），所以按档位换算。

这里还踩过一个纯格式的坑：这条链路走的是兼容模式，按 OpenAI 的写法校验，分隔符必须是 `x` 不能是 `*`。传百炼原生的 `1328*1328` 会被上游以 400 打回，报错是 `Field 'size' must use '<width>x<height>'`。

**二、局部重绘走异步任务。** 必须调万相图像编辑的 `POST {host}/api/v1/services/aigc/image2image/image-synthesis`，带 `X-DashScope-Async: enable` 提交，拿 `output.task_id` 后轮询 `GET {host}/api/v1/tasks/{id}`，2 秒一次、5 分钟封顶。输出尺寸跟随底图，所以这条路径不发送尺寸。

`dashScopeHost` 因此要能从兼容模式地址（`…/compatible-mode/v1` 或 `…/v1`）还原出主机前缀，因为异步任务接口挂在 `/api/v1/...` 下，不在兼容模式路径里。

**三、蒙版极性是反的。** 本地这套是「透明 = 要重绘」，百炼是「白色 = 要重绘」，所以发出去之前要先把蒙版反相：

```go
if _, _, _, alpha := source.At(x, y).RGBA(); alpha < 0x8000 {
	target.SetRGBA(x, y, color.RGBA{R: 255, G: 255, B: 255, A: 255})  // 要重绘，写白
	continue
}
target.SetRGBA(x, y, color.RGBA{A: 255})                              // 保留，写黑
```

### 那个像「没权限」的 403

对应症状里的第三条。百炼把「生成」和「编辑」分在两个协议上：万相图像编辑系列（名称里带 `imageedit`，旧版局部重绘模型带 `painting`）吃 mask；千问图像既不吃 mask、也不支持异步调用。

选错模型时，上游回的是 403 `AccessDenied`「current user api does not support asynchronous calls」。这句话和「密钥没权限」长得几乎一样，用户根本看不出是模型选错了。

所以加了一条只能靠模型名判断的判据：

```go
func dashScopeSupportsMaskEdit(model string) bool {
	name := strings.ToLower(strings.TrimSpace(model))
	if name == "" {
		return false
	}
	return strings.Contains(name, "imageedit") || strings.Contains(name, "painting")
}
```

同一条判据前后端各用一次，用途不同：前端 `core.ts` 的 `dashScopeSupportsMaskRepaint` 用来**不把模型列出来**，后端用来**在提交前拦住**并给出可执行建议：

> 百炼的蒙版局部重绘只能用万相图像编辑模型（如 wanx2.1-imageedit）；当前模型走的是同步图像生成接口，不接受蒙版。请在「系统设置 → AI」里为该模型源添加一个图像编辑模型后再试。

前端这层筛选取舍得说清楚：`RepaintModelOption.supportsMask` 只作用在「局部重绘」这一档。`qwen-image-2.1-pro` 是条好用的文生图 / 图生图模型，只因为不吃蒙版就把它从所有下拉里抹掉，是过度收缩。

```ts
const repaintModelOptions =
  mode === 'repaint' ? models.options.filter(option => option.supportsMask) : models.options
```

## 第二版：模型不吃蒙版，那就自己裁

改到这里，功能是通的，但前提很脆：非得有个支持 mask 协议的模型。换个供应商、换个模型，局部重绘就直接消失。

于是换了个思路。`frontend/src/lib/ai-image/repaint-crop.ts` **不再把蒙版发给 provider**，改成三步：

1. 从蒙版笔迹求出重绘区域的包围盒，外扩一圈上下文，从目标图裁出「裁片」，缩放进 512 到 4096；
2. 裁片加用户提示词加一句自动生成的位置提示（九宫格方位），交给模型做普通图生图；
3. 结果按原坐标贴回目标图，只在蒙版区域内（边缘羽化）合成，蒙版外像素级不动。

于是任何图生图模型都能做局部重绘，上文那层 `supportsMask` 筛选也从「必须」降级成「只是为了更准」。

### 先量出要改的那块在哪

包围盒在探针上量，`MASK_BBOX_PROBE_MAX_EDGE = 512`。4096² 的原图按原分辨率扫 alpha 要 64MB ImageData，在探针上扫完把坐标按比例还原，再外扩 1 个探针像素，避免缩放误差吃掉边缘。判定阈值 `MASK_REPAINT_ALPHA_MAX = 200`，和 `maskHasInpaintArea` 是同一条。

蒙版必须与目标图同尺寸，这里再拦一次，给的是人话：`蒙版尺寸与目标图不一致，请重新涂抹蒙版`。

外扩是为了给模型留上下文，但别大到淹没主体：

```ts
const CROP_PAD_RATIO = 0.25   // 相对包围盒较长边
const CROP_PAD_MIN_PX = 24
```

包围盒大到接近整图（`WHOLE_IMAGE_AREA_RATIO = 0.85`）时直接退化成整图，不裁剪、也不加方位提示，那时没有「其余部分」可言。其余情况按九宫格翻成一句英文：

```ts
const col = centerX < width / 3 ? 0 : centerX < (2 * width) / 3 ? 1 : 2
const row = centerY < height / 3 ? 0 : centerY < (2 * height) / 3 ? 1 : 2
const phrase = row === 1 && col === 1 ? 'center'
  : `${['upper', 'middle', 'lower'][row]}-${['left', 'center', 'right'][col]}`
return `Apply the requested edit only to the ${phrase} area of the image; keep the rest of the image exactly as it is.`
```

裁片本身也要落进 512 到 4096。长边还能压到 `CROP_MAX_LONG_EDGE = 2048` 且不破坏短边 512 下限时，再压一档控制请求体积。重编码格式随目标图：PNG 保持透明通道，其余编 JPEG。

提示词的拼装顺序在 `run.ts` 的 `runCropRepaint` 里，三段用空行分隔：

```ts
const prompt = [request.prompt, REPAINT_SUBJECT_PROMPT, plan.regionHint].filter(Boolean).join('\n\n')
```

中间那句主体约束是固定的：

> Restrict your changes to the main subject inside this region; the background and every pixel outside the subject must stay exactly the same as in the input image.

画笔涂抹难免越过主体轮廓一圈，靠这句话把模型的编辑压回区域内的主体上。注意输出尺寸也换了：发给模型的是 `plan.imageSize`（按**裁片**比例挑的档），不再是用户选的整图尺寸，这样贴回时的取材裁切最少。

### 贴回去时，只认「涂过」且「真改了」的像素

这是整条链路里最容易做糊的一步。

生图模型会重排**整张裁片**的像素，连没动过的背景也带 ±10 上下的重合成噪声；而涂抹超出主体的那部分，模型多半根本没改。如果直接把整张结果盖回去，成图会整体发糊、背景被重排。

所以贴回的区域取两个集合的交集。第一层是结果本身，用 cover 取材，宁可裁掉一点也不拉伸：

```ts
const source = coverDrawRect(result.naturalWidth, result.naturalHeight, rect.width, rect.height)
layerCtx.drawImage(result, source.x, source.y, source.width, source.height, 0, 0, rect.width, rect.height)
```

第二层是变更门控，逐像素的软坡：

```ts
const DIFF_GATE_LOW = 10    // 低于它视作未改动（模型噪声）
const DIFF_GATE_HIGH = 40   // 高于它视作真改动
gate[pixel] = Math.min(1, Math.max(0, (distance - DIFF_GATE_LOW) / (DIFF_GATE_HIGH - DIFF_GATE_LOW)))
```

`distance` 取 RGB 三通道差的最大值。软坡让边界自然羽化，也容忍模型对背景的无害微扰；阈值偏大时宁可少贴、保留原图，不会出现糊斑。

然后蒙版反相、羽化，最后用两次 `destination-in` 把三层乘起来：

```ts
for (let index = 3; index < clipImage.data.length; index += 4) {
  clipImage.data[index] = 255 - clipImage.data[index]   // 透明＝重绘，反相成「要贴上的区域」
}
featherCtx.filter = `blur(${Math.max(2, Math.round(Math.min(rect.width, rect.height) * 0.02))}px)`

// 最终贴回区域 = 蒙版（羽化） ∩ 变更门控
gateCtx.globalCompositeOperation = 'destination-in'
gateCtx.drawImage(featherCtx.canvas, 0, 0)
layerCtx.globalCompositeOperation = 'destination-in'
layerCtx.drawImage(gateCtx.canvas, 0, 0)
```

羽化半径取裁片短边的 2%、下限 2px。最后把原图整张画上、再把 layer 按 `rect` 贴回即可。

蒙版保证不越出涂抹范围，门控把模型「没真正改动」的像素换回原图，成图与原图的差异只来自真实编辑。

### 什么时候还得回落老路

```ts
if (request.mode === 'repaint' && target?.dataUrl && request.maskDataUrl) {
  return runCropRepaint(request, target.dataUrl, request.maskDataUrl, context)
}
```

拿不到目标图像素时（MO云 的云图只有一个 id，字节在官网对象存储里），落回「蒙版直发 provider」。这个分支保证功能不会因为通道不同而消失，只是云通道那条仍然依赖模型支持 mask 协议。

## 生成出来只是半成品，还得进资源库

渲染进程拿到的是 data URL，要把它变成资源库里的真资产，走 `app_local_repaint.go` 的 `RegisterLocalAssetRepaintResult`。

字节**不跨绑定**。参数里图是一段 URL（本地 editor-ai 的临时地址或 data URL），Go 侧先 `DownloadMessageImageToFile` 落到临时文件再读回来，30MB 的结果不必做一次 JSON 序列化。

文件名在 Go 侧生成：`<源文件名>_repaint_<hex><ext>`。扩展名**从实际字节嗅探**，绝不从 URL 或源文件名继承，一个对 PNG 请求回 JPEG 的供应商不该在磁盘上被标错：

```go
base := strings.TrimSuffix(strings.TrimSpace(sourceName), filepath.Ext(sourceName))
// base 为空时回落 "photo"
return base + "_repaint_" + hex.EncodeToString(token) + repaintImageExtension(data), nil
```

真正落库在 `local_library/repaint.go` 的 `RegisterRepaintResult`，几条硬规则：

| 规则 | 为什么这么定 |
| --- | --- |
| 结果写到源照片**同一个目录**下的新文件 | 让生成图和它的来源在资源库里挨着，用户一眼能找到被改前和改后 |
| 重名不覆盖，也不无条件编号 | `availableRepaintPath` 有名字就用，占用了才回落库里的 `(n)`；生成名带随机 hex，本来就不太会撞，无条件编号反而会把这个事实藏起来 |
| 只接受 `image` / `live-photo` | 视频、音频、未分类没有像素可当参考，在发请求前就拒掉 |
| 提示词超限**拒绝**而不是截断 | `maxRepaintPromptLength = 8000` 是存储护栏，不是 provider 限制；超了要报错让用户看见，而不是悄悄改掉他写的东西 |
| 派生边和标签**同事务** | `insertAssetDerivationWithTag`，一个注册成功却缺标签的结果就是一次静默的半写 |

最后一条值得展开。结果图除了派生边（谁改自谁），还会自动挂上「AI改图」标签。之前生成图只能靠文件名里的 `_repaint_<hex>` 和详情面板的来源区区分，标签区里什么也看不到，想「只看 AI 生成的图」只能靠文件名搜索。

标签按 `name_key` 查，用户自己建过同名标签就复用那一行的 id 与颜色，不会撞 `UNIQUE`，也不会多出一条几乎同名的重复项。

写入成功后发两个事件：`asset_derivations_updated`（派生关系变了）和 `organization_updated`（标签与计数也变了，工作台要重载组织数据而不只是网格）。返回 DTO 里 `previewStatus` 固定是 `"pending"`，新写入必然重新排队缩略图，渲染进程据此先显示生成中状态，等 `asset_preview_updated` 到达。

同样的道理也解释了「注册只在生成成功之后」：失败的、被取消的、上游报错的生成都不会在库里留下半个资产。

## 回看：记录里存的是蒙版，不是笔迹

「我的作品 → AI图片」的台账落在 IndexedDB（库 `mo-gallery-ai-images`，对象仓 `jobs`）。记录里除了展示字段，还并存一份参数快照：

```ts
export interface AiImageJobRequest {
  prompt: string
  mode: 'text' | 'image' | 'repaint'
  channel: RepaintChannel
  imageSize: RepaintImageSize
  model?: string
  conversationTitle?: string
  target?: AiImageJobImage      // 要被按照提示词修改的那张底图
  reference?: AiImageJobImage   // 只提供风格 / 构图
  maskDataUrl?: string          // PNG data URL，透明区域才是要重绘的部分
}
```

两者刻意并存：记录上的 `prompt` 是给人读的最终提示词，快照要连同通道、尺寸、模型、两张输入图、蒙版一起原样重放。字段全是可选的，早于这次改动的记录读回来照样能显示（只是没有原图、也没有重试入口），因此不需要升 IndexedDB 版本，也没有数据迁移。

三个消费者共享同一套回落规则，任何一处单独「优化」都会让重试出来的东西和当初那次不是一回事：

- `run.ts`：旧快照只有 `reference`，那时它就是被改的底图，所以 `target` 回落 `request.reference`；参考图只在新快照且 `mode === 'image'` 时才发（局部重绘多一张图 provider 直接拒，而旧快照那张已经被当底图用掉了）。
- `AiImageJobCard.tsx`：详情里那格输入图的标题跟着 `mode` 走，图生图叫「参考图」，局部重绘叫「原图」。
- `AiImagePage.tsx` 的 `jobSeedFromRecord`：点「修改」回显参数时，**通道不一致就不带回输入图**。快照记的是提交时那条通道，而 `GenerateAiImage` 按当前云服务分派；把本地那份 data URL 送给官网、或把云图 id 送给本地 AI 服务，两边都会静默退化成文生图，比不做更糟。

原图在快照里的形态也按通道分。本地存**真正发给 provider 的那份 data URL**（长边不超过 1536 的重编码结果），查看与重试都用它，不依赖资源库是否打开、也不依赖源文件还在原路径；MO云 只存 `cloudImageId` 加一个预览地址。

详情里「点原图叠一层高亮」的交互在 `RepaintRegionOverlay.tsx`，有两个刻意的设计。一是画布按**蒙版自身像素尺寸**绘制、显示交给 CSS 的 `object-contain`，两张同比例的位图落在同一个盒子里必然逐像素重合，所以不必测量布局尺寸，窗口缩放或文案换行都不会让高亮错位。二是蒙版解码失败就什么都不画，宁可不显示这一层，也不要糊一层位置不明的高亮。

回看时那片高亮是把蒙版反相叠出来的：先铺满同一枚高亮色，再用 `destination-out` 把蒙版抠掉，剩下可见的恰好是蒙版里透明的部分。

```ts
ctx.fillStyle = MASK_PREVIEW_COLOR
ctx.fillRect(0, 0, width, height)
ctx.globalCompositeOperation = 'destination-out'
ctx.drawImage(mask, 0, 0, width, height)
```

极性必须与蒙版严格互补。画反了会把从没动过的地方标成重绘区域，比不显示这一层更误导，`frontend/tests/mask.test.mjs` 专门有一条用例断言这个合成方向。

## MO云 那边没有 mask 契约，就别装作有

MO云 的 AI 生图 / 改图由官网代发（`POST /api/ai/image-edits`，只收 `sourceImageId`、`prompt`、`size`，字节由官网自己从对象存储取），**目前没有 mask 字段**。

这件事在四个地方保持一致，缺一处就会变成「涂抹完全没起作用、还烧了一次配额」：

1. 数据层直接抛错，不静默降级：

```ts
if (params.maskDataUrl) {
  throw new OfficialCloudError('MASK_UNSUPPORTED', 'MO云 通道暂不支持局部重绘，请切换到自部署模式后重试', 400)
}
```

2. `loadRepaintImageModels('cloud')` 返回的占位选项 `supportsMask: false`；
3. 生图页「生成方式」里的「局部重绘」在 MO云 下是禁用项，带 `title` 说明为什么；停在它上面时切回云端会自动退回「图生图」；
4. 从记录点「修改」时通道对不上，`jobSeedFromRecord` 只在通道一致时带过蒙版。

这也解释了为什么 `RepaintChannel`（`'local' | 'cloud'`）必须**由调用方显式给出、不能按当前云服务去猜**。本地资源库在 MO云 模式下照样打开，那是两条独立的资源库，它永远走本地 editor-ai；反过来说云端资源库在自部署模式下也不该落本地盘。用「当前云服务」推断会把这两种情况都判错。

## 踩坑汇总

前面散着讲的那些，集中成一张表，方便以后对着症状查：

| 现象 | 根因 | 护栏 |
| --- | --- | --- |
| `mask 与 image 尺寸不符` | 用显示画布尺寸渲染蒙版 | 导出后断言 + Go 侧「只需一张图」校验 |
| 涂抹没效果、白烧配额 | 涂完又全擦掉，蒙版全不透明 | `maskHasInpaintArea` 扫 alpha，禁用「确定」 |
| 403 `AccessDenied ... asynchronous` | 百炼选了不吃 mask 的模型 | `dashScopeSupportsMaskEdit` 提交前拦截 |
| 400 `Field 'size' must use '<width>x<height>'` | 把百炼原生的 `1328*1328` 写进了兼容模式 | `dashScopeSizeForModel` 统一用 `x` |
| `The height/width should be between 512 and 4096` | 高像素照片原样直传 | `repaintSourceScale` 收进区间 |
| 蒙版超过 4MB | 涂抹范围过大 / 蒙版被编成 PNG 巨图 | `maxRepaintMaskBytes` 本地先拦 |
| 蒙版编辑器空白、涂了看不见 | rAF 句柄未归零，守卫永久为真 | 先取消再排帧 + 卸载时归零 |
| 成图整体发糊、背景被重排 | 直接把整张结果贴回 | 变更门控 + 蒙版羽化 |
| 云通道涂抹无效 | 官网端点没有 mask 契约 | `MASK_UNSUPPORTED` 直接报错 |

## 验证

这套逻辑的验证主要靠纯函数单测，因为最难的几处恰好都被抽成了不碰 DOM 的纯逻辑：

- `frontend/tests/mask.test.mjs` 钉住合成极性（预览与蒙版必须互补）、`maskHasInpaintArea` 对「涂了又擦」的判定、回看高亮的反相方向；
- `frontend/tests/photo-repaint.test.mjs` 直接 bundle `core.ts` 与 `client.ts`，覆盖请求体拼装、SSE 三种事件的解析、`repaintSourceScale` 的边界（超上限、短边不足、极端长宽比）与 `supportsMaskRepaint` 的模型判据。

协议层那几处只能靠真实上游验证，所以百炼的模型判据特意做成前后端共用同一条规则：前端不让选，后端再拦一次，任何一处漏了另一处还在。

## 复盘小结

1. **别把显示尺寸当成交付尺寸**。同一片像素要经过显示画布、缩略图、原图三层缩放，任何一次「顺手用当前尺寸」都会在几百公里外的上游被打回，而错误信息不会告诉你是哪一层错的。
2. **极性这类约定，只在边界上转一次**。本地一律「透明 = 要重绘」，反相只发生在发给百炼之前。如果每处都各自转一次，迟早会有一处漏转，而且症状是「改了没效果」，比报错更难查。
3. **能筛就别让用户试错**。百炼那个 403 长得像权限问题，靠文案是解释不清的，直接不把不吃 mask 的模型列进局部重绘下拉，是最省事也最不容易被告状的做法。
4. **客户端合成是拿「协议兼容性」换「全局上下文」**。裁片方案让任何图生图模型都能做局部重绘，代价是模型看不到裁片之外的东西，需要大幅出画的编辑会受限。这个取舍值得，但得提前说清楚。
5. **贴回只认「涂过」且「真改了」的像素**。生图模型会重排整张裁片，连背景都带噪声，不做变更门控就会整体发糊；反过来门控阈值偏大时宁可少贴，保留原图总比糊斑好看。
6. **只在成功后落库**。失败的、被取消的、上游报错的生成不该在资源库里留下半个资产，注册这步放到最后，天然就不必写回滚。
