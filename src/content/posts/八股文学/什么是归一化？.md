# 什么是归一化

归一化是 WAF 在匹配规则之前做的一次改写：把同一条语句的各种编码变体，还原成唯一形态，让一条规则覆盖全部写法。

## 位置

请求进入 WAF 后的处理顺序：TLS 终结 → 协议解析 → **归一化** → 规则匹配 → 处置。

前提是 WAF 终结了 TLS。链路加密时 WAF 看到的是密文，归一化无从谈起，这也是 HTTPS 站点接 WAF 必须先传证书的原因。业务自己做端到端加密的情况，WAF 能拿到明文也读不懂字段，规则同样失效。

## 为什么需要

规则是按标准形态写的，比如 `@rx (?i)union\s+select`。把语句换个编码，正则就匹配不上。下面六条指向同一句话：

| 变体 | 报文里的样子 | 还原手段 |
|---|---|---|
| 原文 | `1' OR 1=1--` | — |
| URL 编码 | `1%27%20OR%201%3D1--` | URL 解码 |
| 双重编码 | `1%2527%20OR%201%3D1--` | 解码两次 |
| 大小写混写 | `1' oR 1=1--` | 统一大小写 |
| 注释插入 | `1'/**/OR/**/1=1--` | 剥离注释 |
| 换行替代空格 | `1'%0aOR%0a1=1--` | 空白压缩 |

每种写法单写一条规则，规则集膨胀六倍，而且补不完。归一化把成本从「规则数量」转移到「解析质量」，这是它存在的唯一理由。

## 具体改哪些内容

按处理顺序：

- **URL 解码**。解码一次还是循环解码到稳定，各家实现不同，这个次数本身就是绕过点。
- **Unicode 与宽字节**。`%u0027` 这类 IIS 时代的老写法，以及 GBK 宽字节 `%bf%27`。
- **HTML 实体还原**。`&#39;`、`&apos;`、`&lt;` 还原成原字符。
- **大小写统一**。或者在规则里加 `(?i)`，两种做法取其一即可。
- **剥离注释**。`/**/`、`--`、`#` 在 SQL 里是注释，在等价性上是空白。
- **空白压缩**。多个空格、tab、换行压成单空格，`OR%0a%0a1=1` 与 `OR 1=1` 才算同一条。
- **路径规范化**。`/a/../b` 还原成 `/b`，`//api///user` 还原成 `/api/user`。
- **分块传输重组**。chunked 编码的 body 要拼回完整内容再匹配，否则规则看到的是一堆长度头。
- **Content-Type 容错**。声明成 `text/plain` 实际内容是 JSON，也得按结构解析，否则把整个 body 当字符串匹配容易漏。
- **同名参数处理**。`?id=1&id=2` 取第一个还是最后一个，必须与后端保持一致。

**最容易混的一处**：最后这条。HTTP Parameter Pollution 的绕过原理就在这里，WAF 取第一个、后端取最后一个，`?id=1%20union%20select...` 排在后面就能穿过检测。

## 与后端解析不一致就是绕过

归一化的判定标准只有一条：**和后端解析出的形态一致**。四个常见的不一致点：

- **解码次数**：WAF 解一次，框架解两次。双重编码的载荷在 WAF 眼里仍是编码态。
- **参数取值**：同名字段的取前取后不同，见上条。
- **路径处理**：后端把 `/api/../admin` 归一成 `/admin`，WAF 没做路径规范化，规则按 `/api/...` 判，判定落在错误的规则组上。
- **字符集**：WAF 按 UTF-8 解码，后端按 GBK，宽字节字符在两边长度不同。

这类问题的共同特征：WAF 日志里一切正常，攻击实际生效。定位绕过时，第一件事是比对 WAF 记录的归一化结果和后端实际收到的内容。

## 它不做的事

- 不做业务校验。越权、刷券、批量导出这类请求，归一化之后依然完全合法。
- 不判断语义是否恶意。归一化只产出字符串，判断交给规则；语义级检测（如 `@detectSQLi`）是归一化之后另一层的事。
- 不修改数据。它是只读的预处理，改写结果只给规则引擎看，不会改变转发给后端的内容。

## 怎么验

- 拿一条已知 payload，做编码、双重编码、注释插入三组变体打过去，看是否全部命中同一条规则。
- 看日志里有没有「归一化后内容」字段，多数 WAF 会记录，这是排查误杀和绕过最直接的证据。
- 把这批变体固化成回归用例。规则改动、换 WAF 厂商、升级版本之后各跑一遍。

## 一句话

归一化决定了规则能覆盖多少写法。规则数量堆得再多，归一化缺一环，绕过去只需要换一种编码。
