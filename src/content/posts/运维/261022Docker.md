## 基本概念

- 镜像、容器、仓库三者的关系，以及分层存储和写时复制（overlay2）。这是后面所有“为什么改一个文件要重新 build”的根。
- 容器本质是带 namespace 隔离和 cgroup 限制的普通进程，不是虚拟机。如果这点讲清楚，读者就不会再问“容器里能不能装 systemd”。
- 生命周期状态：created / running / paused / exited / dead，以及 `restart` 会在什么情况下无效。
- **加分但很值**：容器内 1 号进程不转发信号这个坑。它能解释后面“为什么 `docker stop` 要等十秒才强杀”。

## 配置文件

- Dockerfile 常用指令逐个过一遍，重点放在 `COPY` 与 `ADD` 的区别、`CMD` 与 `ENTRYPOINT` 组合时的覆盖规则，以及 exec form 和 shell form 对信号的影响。
- 构建缓存与层顺序：先 `COPY` 依赖清单再装依赖，最后才 `COPY` 源码。这条决定了改一行代码时是等 3 秒还是等 3 分钟。
- `.dockerignore`。少了它，`node_modules` 和 `.git` 会被塞进构建上下文。
- 多阶段构建。讲一个具体例子，比讲概念有用得多。
- **坑位提醒**：基础镜像选择。alpine 用 musl，时区和 glibc 兼容问题能卡半天；`latest` 标签不要用。
- docker-compose.yml 的结构也应该放在这一节：`services` / `volumes` / `networks`，以及 `depends_on` 默认只等容器起来、不等服务就绪，要配 `healthcheck` + `condition: service_healthy`。


## 环境变量

- `ENV`（构建期+运行期，进镜像）和 `ARG`（仅构建期）的区别与优先级。
- **最容易混的一处**：compose 的 `.env` 是给 compose 文件本身做变量替换用的，`env_file` 才是把变量注入容器。两个都叫“环境变量文件”，行为完全不同。
- 优先级链：`docker run -e` > `--env-file` > 镜像内 `ENV`。写清楚，排障时直接照着查。
- 密钥不要用 `ARG` 或 `ENV` 传，构建历史里能翻出来。用 BuildKit 的 `--mount=type=secret` 或挂载文件。
- 顺手带上 `TZ` 和 locale：容器默认 UTC，中文乱码大多出在这里。


## 部署方式

- `docker run` 的参数表：`-d --name -p -v -e --env-file --restart --network --memory --cpus --ulimit`。做一张表，比逐条列文字更容易查。
- 端口绑定的安全细节：`-p 127.0.0.1:8080:80` 和 `-p 8080:80` 的差别是是否直接暴露到公网。
- 三种挂载：bind mount、volume、tmpfs，以及 UID/GID 不匹配导致“容器写不进目录”的经典问题。
- 网络：默认 bridge、自定义 bridge（有 DNS，能按服务名互访）、host 模式各自适用什么场景。
- `restart` 策略四个值的行为差异，特别是 `always` 和 `unless-stopped` 只差一个“手动停过没有”。
- compose 实战命令：`up -d`、`down`（注意 `-v` 会把数据卷一起删掉）、`logs -f`、`exec`、override 文件做开发/生产差异。
- **必须写的运维项**：日志驱动默认的 `json-file` 不轮转，磁盘会被写满。配 `max-size` / `max-file`。
- 升级与回滚流程：换 tag → `pull` → `up -d`，数据卷不动。
- 优雅停机：`--stop-timeout`、`--init`，接上前面 1 号进程那个坑。

## 容器打包

- 完整链路：`build` → `tag` → `push`。
- 镜像名就是地址。`docker push` 没有「指定推到哪里」的参数，目标全部写死在镜像名里：`[仓库域名[:端口]/]命名空间/仓库名[:tag]`。不写域名默认 Docker Hub，不写命名空间默认 `library`（`library` 是官方镜像的位置，个人账号没有推送权限），不写 tag 就是 `latest`。所以 `docker tag` 干的事不是复制镜像，是给它再挂一个「带地址的名字」。
- 瘦身四招：多阶段、合并 `RUN`、清包管理器缓存、用 `dive` 看每层大小。
- **导出迁移要分清**：`save`/`load` 搬镜像（保留元数据），`export`/`import` 搬容器文件系统（丢 `CMD`、`ENV`、历史）。这两个混用是常见事故。
- 私有仓库：`registry` 或 harbor 搭建，`insecure-registry` 怎么配。
- 跨架构构建：`buildx --platform linux/arm64`。现在 arm 服务器不少，这条迟早用得上。
- 加一点安全：非 root 的 `USER`、`trivy` 扫漏洞、镜像签名。



## docker网络

- 一句话答案：两个容器挂在**同一张用户自定义 bridge 网络**里，然后把容器名当主机名用。
- 为什么默认 `bridge` 不行：它没有内置 DNS，容器之间只能靠 IP（重启就变）或早废弃的 `--link`。自定义网络自带 127.0.0.11 的 DNS，容器名和 `--network-alias` 都能直接解析。
- 独立启动的最小流程：

```bash
docker network create app-net
docker run -d --name mysql-db --network app-net \
  -e MYSQL_ROOT_PASSWORD=xxx -v mysql-data:/var/lib/mysql mysql:8.0
docker run -d --name api --network app-net \
  -e DB_HOST=mysql-db -e DB_PORT=3306 -p 8080:8080 my-api:1.0
```

- 应用侧连接串写 `mysql-db:3306`。**容器间通信不需要 `-p`**，`-p` 只解决宿主机和外部访问。数据库更不要 publish，等于白送一个公网攻击面。
- 同一个 compose 项目里的服务本来就在 `<项目名>_default` 这张网络上，直接用 service 名互访，不用额外配置。
- 一个 run 起的容器 + 一个 compose 项目，或两个独立 compose 项目：网络要在外面先建好，compose 里声明 `external: true`。

```yaml
services:
  api:
    networks: [app-net]

networks:
  app-net:
    external: true
```

- 一个容器可以同时接多张网络（`docker network connect` 或 compose 里列出来），用这个做隔离：DB 只挂在 internal 网络上，API 挂两张，既连得到 DB 又出得去外网。

```yaml
networks:
  db-net:
    internal: true   # 无外部出入口
  app-net: {}
```

- 跨主机通信是另一套（overlay，靠 swarm 或 k8s）。单机部署不用碰。

### 踩过的坑

- 不要硬编码 IP。容器重建 IP 就变，`--ip` + 自定义子网能固定但没必要。
- `depends_on` 只保证启动顺序，不保证 DB 就绪。要 `healthcheck` + `condition: service_healthy`，应用侧还得有自己的重试。
- 网络通 ≠ 能连上。MySQL 8 账号 host 不是 `%` 时，报 `Access denied for user 'root'@'172.18.0.5'`，看着像网络问题，其实是授权问题。
- 容器要访问宿主机上的服务：Linux 加 `--add-host=host.docker.internal:host-gateway`，或者直接 `--network host`（性能最好，但端口和宿主机抢，隔离也没了）。

### 排障三招

```bash
docker network inspect app-net          # 看谁在这张网里、各自 IP
docker exec -it api nslookup mysql-db   # DNS 解析通不通
docker exec -it api nc -zv mysql-db 3306 # 端口通不通
```

镜像精简时 `ping` 往往不存在，别拿它当判断依据。



## 常见场景

### 私有仓库，推送到服务器docker部署/升级

链路就四步：本地或 CI 构建 → 打 tag → push 到私有仓库 → 服务器 pull 后 `up -d`。
	
#### 1. 仓库先起来

```bash
docker run -d --name registry --restart unless-stopped \
  -p 5000:5000 \
  -v /opt/registry:/var/lib/registry \
  -e REGISTRY_STORAGE_DELETE_ENABLED=true \
  registry:2
```

- registry 默认只认 HTTPS，`localhost` 除外。生产套一层 nginx + 证书；内网自签就把 `ca.crt` 放到每台机器的 `/etc/docker/certs.d/<域名>:5000/ca.crt`，比全局开 `insecure-registries` 干净。
- 项目多、要按人分权限，直接上 Harbor。`registry:2` 只是个存储，没有 UI、没有 RBAC、没有扫描。

#### 2. 命名与 tag

- 镜像名必须带仓库地址：`registry.example.com/ns/app:1.2.3`，否则默认往 Docker Hub 推。
- 双 tag：版本号给人看（`1.2.3`），commit sha 给回滚定位（`sha-a1b2c3d`）。
- 别把 `latest` 理解成「最新版本」。它只是不写 tag 时的默认值，指向最后一次被 push 成 `latest` 的那个镜像，和「最新 commit」「最新的 tag」都没有自动关系；Docker 不会主动比较版本号大小。
- 仓库里只有一张 `tag → digest` 的名字表，`latest` 是其中独立的一行，不会跟着别的 tag 走，也没有「自动兜底到最新」这种机制。只推了 `1.2.4` 没推 `latest`，`docker pull app` 会直接报 `manifest unknown`——这就是它在查表、而表里没这一行。
- **git 仓库更新 ≠ 镜像更新**。两者之间没有任何自动同步，中间必须有人或 CI 去 build + push。tag 长期不动而主分支一直在提交，说明这条链路断了，而不是「镜像会自动跟上」。这种断法不报错：`pull` 到的还是老镜像，服务照跑，改的 bug 就是不生效。
- 想跟着 master 最新代码走，用 sha tag，不用 `latest`：CI 里 `docker build -t app:sha-$GIT_SHA -t app:latest`，推两个 tag 只多花一次 manifest 的时间（层已经在了）。部署用 `sha-`，`latest` 只是给人看的别名。
- 只有一条主分支、一个人部署的小项目，只推 `latest` 也能跑得挺好。代价是覆盖那一刻旧镜像就失去名字了，出问题没有「上一个版本」可退。最低成本的补救不是建整套版本号体系，是 tag 里带上短 sha，两行 shell 的事。
- **不要在同一 tag 上重复 push**。tag 名没变，编排层就认为「镜像没换」，靠 `--pull always` / `--force-recreate` 去补太脆弱；换了 sha 就是天然的一次新部署。

#### 3. 登录

```bash
docker login registry.example.com          # 交互输密码
echo "$TOKEN" | docker login registry.example.com -u ci -p --password-stdin
```

凭据存在 `~/.docker/config.json`，只是 base64，不是加密。服务器上给一个只读账号，别用管理员。

#### 4. 服务器侧用变量接 tag

```yaml
services:
  api:
    image: registry.example.com/ns/app:${TAG:?TAG required}
    restart: unless-stopped
```

`.env` 里写 `TAG=1.2.3`。`${TAG:?}` 的意思是没设就报错——防止手滑拉到空值或 `latest`。

#### 5. 升级和回滚都是改一行

```bash
# 升级
sed -i 's/^TAG=.*/TAG=1.2.4/' .env
docker compose pull
docker compose up -d --remove-orphans

# 回滚：改回旧 tag 再来一次
sed -i 's/^TAG=.*/TAG=1.2.3/' .env
docker compose up -d
```

- `up -d` 只重建容器，命名卷不动，数据还在。
- 回滚的前提是旧镜像还在本地。`docker image prune -a` 会把回滚能力一起清掉，用 `--filter until=168h`，或者按 tag 留最近三个。

#### 6. 坑

- **数据库迁移不可回滚**。镜像能退回去，schema 退不了。迁移脚本写前向兼容：先加列，不删列，隔一版再清。
- registry 磁盘只涨不降。`REGISTRY_STORAGE_DELETE_ENABLED=true` 只是允许删，删完还得跑 garbage-collect 才真释放空间。
- 单机 compose 没有滚动发布，`up -d` 那几秒服务是不可用的。要零停机，前面挂反代做蓝绿，或者干脆上 swarm / k8s。
- 服务器和 registry 跨机房时拉镜像很慢，registry 就近部署，或者用 Harbor 的复制做多地分发。
- 开机自启别指望 `restart: unless-stopped`——容器没起来它管不了。写个 systemd unit 跑 `docker compose up -d`。
