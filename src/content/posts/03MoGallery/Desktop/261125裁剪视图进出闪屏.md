# 同一张图，进出各闪一次

本地资源库的大图预览里点「裁剪」，画面会切进同一个外壳下的编辑器视图。功能本身没坏，但切换过程一直不干净：

1. 从裁剪里点关闭回到浏览，图片会**先白掉一半、再慢慢补全**。
2. 点「裁剪」进去，画面会**空一下**再出图。
3. 修完第 2 条之后，进入反而变得更闪——图片先按一个尺寸出现，紧接着跳成另一个尺寸。

真正把问题拆开的，是一句对照观察：

> 从裁剪页点关闭，进入图片查看时没有闪屏；但从图片浏览点裁剪时，会有闪屏。

**退出不闪、进入才闪**，说明「同一帧里把旧内容藏起来」这条路没问题，问题出在「新内容得有图才能画」。这句话把排查范围从「渲染性能」直接缩小到了「挂载时序 + 几何一致性」。

## 复现环境

| 项目  | 本次环境                                                      |
| --- | --------------------------------------------------------- |
| 应用  | Emulsion Desktop（Electron 外壳 + 复用 React 渲染层 + Go sidecar） |
| 前端  | React 19、Vite                                             |
| 外壳  | Electron 33                                               |
| 系统  | Windows 11                                                |
| 视口  | 1441 × 901                                                |
| 素材  | 6000px 级 JPEG（P1109264 这类全画幅原图）                           |

后面所有结论都来自这台机器和这组素材，没有覆盖混合 DPI 多屏、集显/独显切换这些场景。

## 先看清外壳：这是子视图切换，不是新窗口

`PhotoPreviewFrame` 是浏览、播放器、文件预览、裁剪共用的一层外壳：顶栏 + 舞台，外壳本身不重建。裁剪视图通过 `overlay` 作为同层视图塞进来，覆盖范围、底色、层级都由外壳负责。

```tsx
// renderer/src/components/admin/PhotoPreviewFrame.tsx（简化）
<div className={`${bounded ? 'absolute inset-0 z-20' : 'fixed inset-x-0 bottom-0 top-9 z-[70]'} flex flex-col bg-background`}>
  <div className={overlay
    ? 'pointer-events-none invisible absolute inset-0 flex flex-col'
    : 'flex min-h-0 flex-1 flex-col'}>
    <header>…</header>
    <stage>
      <img className="… object-contain" style={{ height: '100%', transform: `… scale(${zoom})` }} />
    </stage>
  </div>
  {overlay}
</div>
```

两个细节先记住，后面都会用到：

- 大图不是单张 `<img>`，而是**两块槽位叠在同一个舞台里**：一块是当前图、一块是下一张，切换靠显隐对调。两层都已有内容，所以翻页不露底色。
- `<img>` 上挂着 `transform: translate(...) rotate(...) scale(zoom)`，缩放和平移都作用在这一层上。它**不是一张普通静态图片**，一旦重新挂载，就要重新栅格化，代价比看上去高得多。

原始实现是这样切换视图的：

```tsx
{overlay ?? <> <header /> <stage /> </>}
```

看起来天经地义，实际上这就是第一个闪屏的全部根因。

## 症状一：退出裁剪，图片先白一半再补全

**现象**：点关闭回到浏览，图先出现半张，很快补齐。

**根因**：`overlay ?? ...` 是**替换**语义。进入裁剪时，预览整块被卸载——`<img>` 元素、已解码的位图、合成层、栅格，全部丢失。退出时 `<img>` 重新挂载，浏览器要重新解码、再按当前尺寸分块绘制；一张 6000px 的原图缩到 1300px 显示，这个过程按块到达，于是观感就是「先白一半、再补全」。`transform` 层还会额外重建一次合成层。

**修法**：把「替换」改成「盖上去」。预览**始终挂载**，`overlay` 出现时只把它改成不可见：

```tsx
// 卸掉会连已经解码的位图和合成层一起丢，返回浏览视图时大图要从头解码、
// 分块绘制，观感就是「先白掉一半，再慢慢补全」。
<div className={overlay
  ? 'pointer-events-none invisible absolute inset-0 flex flex-col'
  : 'flex min-h-0 flex-1 flex-col'}>
```

几个具体取舍：

- 用 `visibility: hidden`（Tailwind 的 `invisible`），不用 `opacity: 0`。后者仍然命中指针事件，里面的按钮也能被 Tab 聚焦，只是看不见；`invisible` 既不入可访问树，也不进 Tab 序，语义更准。
- **不要**再加 `aria-hidden`。`visibility: hidden` 已经把它从辅助技术里移除了；而如果此时「编辑」按钮还留着焦点，Chromium 会抛 `Blocked aria-hidden on an element because its descendant retained focus`，反而多出一条噪音日志。
- 绝对定位的隐藏层需要一个定位包含块——根节点本身已经是 `absolute`（收进浏览区）或 `fixed`（满窗），天然满足，不需要额外加。

### 中间那次事故：`relative` 把 `absolute` 盖掉

我最初为了「给绝对定位子层一个包含块」，顺手在根节点的 class 里加了 `relative`，写成：

```text
… absolute inset-0 z-20 relative flex flex-col …
```

结果整个预览退回正常文档流：搜索/筛选工具栏还在上面，预览被挤到工具栏下面，宽度也塌了。

原因是 Tailwind 的 position 工具类按**生成顺序**落，不按 class 字符串里的顺序：

```css
.static {}
.fixed {}
.absolute {}
.relative {}   /* 排在 absolute 之后 */
.sticky {}
```

同一个元素上同时出现 `absolute` 和 `relative`，`relative` 赢。**同一属性不要写两个工具类**；而这里根本不需要 `relative`——根节点本来就已经定位了。

这次事故也顺带说明排查顺序的价值：先确认「几何对不对」，再怀疑「渲染快不快」。上一版我盯着解码时序，其实有一半是布局错了。

## 症状二：进入裁剪还是闪

退出修好之后，进入仍然闪。拆开看是**几何、时序、异步加载**三层问题叠在一起，必须分别处理。

### 2.1 几何：三个取景框，两段尺寸变化

预览和编辑器各自把图 contain 到一个框里，但框不一样大：

| 侧 | 舞台内边距 | 图片 fit 到 |
| --- | --- | --- |
| 浏览（`PhotoPreviewFrame`） | `p-5`，两侧共 40px | `舞台 - 40` |
| 编辑器第一版占位图 | `p-6`，两侧共 48px | `舞台 - 48` |
| 编辑器 canvas | `STAGE_PADDING = 56` | `舞台 - 56` |

进入时画面要走两段：`40 → 48 → 56`。整体缩 16px、每边 8px，还要重新居中——这在视觉上读作「跳了一下」，比单纯空一帧更刺眼。这也解释了为什么加上占位图之后「比之前更严重」：**占位图成了夹在中间的第三个尺寸**。

修法是把三处统一到同一个框：

```tsx
/** 必须和浏览大图那边的 `p-5`（两侧共 40px）严丝合缝：编辑器与预览共用同一个外壳，
 *  切进来时图片如果换了个大小，用户就会看到一次「跳一下」的闪烁。 */
const STAGE_PADDING = 40
```

配套把编辑器舞台的 `p-6` 改成 `p-5`，占位图也按 `p-5` 居中 contain：

```tsx
const scale = Math.max(0, Math.min(
  (stage.width - STAGE_PADDING) / freeTurn.boxWidth,
  (stage.height - STAGE_PADDING) / freeTurn.boxHeight,
))
```

注意这里 `stage` 量的是 `clientWidth`（含 padding），所以 `client - 40` 正好等于 `p-5` 的内容盒——两边是同一个盒子，不是「差不多」。

### 2.2 时序：`useEffect` 是画完之后才跑

canvas 挂载时是一块空画布，第一帧由绘制代码填。如果绘制放在 `useEffect` 里，React 会在浏览器**已经绘制**之后才执行它：

```text
commit（canvas 挂载） → 浏览器绘制（空 canvas！） → useEffect（drawImage） → 下一次绘制
```

中间那一帧就是空屏。改成 `useLayoutEffect`（DOM 变更后、绘制前执行）：

```tsx
// 必须在 DOM 提交后、浏览器绘制前把第一帧画进 canvas：canvas 一旦挂载就带着内容
// 出现，才不会在「占位图 → canvas」的接替里闪一帧空白。
useLayoutEffect(() => {
  const canvas = canvasRef.current
  if (!canvas || !image || display.width <= 0 || display.height <= 0) return
  …
}, [image, display.width, display.height])
```

同理，舞台尺寸的测量也从 `useEffect` 挪到 `useLayoutEffect`。否则首帧里 `stage` 还是 `{0,0}`，`display` 为 0，canvas 容器尺寸为 0——等于又空一帧。

### 2.3 最隐蔽的一层：浏览器缓存 ≠ 同步可用

到这一步还是偶发闪一下。原因是编辑器必须**新建**一个 `<img>` / `new Image()` 才有图可画，而 `onload` 无论缓存多热，都是**异步任务**：

```text
new Image() → 任务队列 → onload → setImage → 重渲染 → drawImage → 绘制
```

这条链至少跨 1~2 帧。也就是说，「HTTP 缓存命中」只能省掉网络传输，**省不掉那一帧的空白**。

## 最终方案：把「已解码的元素」直接交接

既然浏览大图上那张 `<img>` 已经把原图解好、画在屏幕上了，就没必要让编辑器再去要一份新图。加一个小小的元素级缓存：

```ts
// renderer/src/lib/ui/decoded-images.ts
const MAX_ENTRIES = 4
const decoded = new Map<string, HTMLImageElement>()

export function rememberDecodedImage(src: string, element: HTMLImageElement): void {
  if (!src || !element.complete || element.naturalWidth <= 0) return
  decoded.delete(src)
  decoded.set(src, element)
  while (decoded.size > MAX_ENTRIES) {
    const oldest = decoded.keys().next().value
    if (oldest === undefined) break
    decoded.delete(oldest)
  }
}

export function recallDecodedImage(src: string): HTMLImageElement | null {
  const element = decoded.get(src)
  if (!element) return null
  if (!element.complete || element.naturalWidth <= 0) {
    decoded.delete(src)
    return null
  }
  return element
}
```

外壳的槽位图在 `onLoad` 里登记：

```tsx
<img
  src={slotSrc}
  // 登记这张已经解码完的元素：编辑器（裁剪）要立刻把同一张图画进 canvas，
  // 拿它同步 drawImage 才不会在切视图时闪一帧空白。
  onLoad={(event) => rememberDecodedImage(slotSrc, event.currentTarget)}
  className="… object-contain"
  style={{ height: '100%', transform: … }}
/>
```

编辑器挂载时**同步**取回，连初值都直接从缓存来：

```tsx
const [image, setImage] = useState<HTMLImageElement | null>(
  () => recallDecodedImage(asset.originalUrl),
)

useEffect(() => {
  const cached = recallDecodedImage(asset.originalUrl)
  if (cached) {
    setImage(cached)
    return () => { disposed = true }
  }
  setImage(null)
  const next = new Image()
  next.onload = () => { if (!disposed) setImage(next) }
  next.onerror = () => { if (!disposed) setLoadFailed(true) }
  …
}, [asset.originalUrl])
```

于是进入时的时间线变成：

```text
点击裁剪 → commit（预览 invisible、canvas 挂载，image 来自缓存）
        → layout effect（量舞台 → setState → 同步重渲染）
        → layout effect（drawImage 画首帧）
        → 浏览器首次绘制：已是完整画面
```

没有任何一帧是空的。占位图于是退化成「缓存没命中」时的兜底——比如那张图在预览里还没加载完。

## 为什么是 `key` 加在编辑器、不加在外壳

```tsx
overlay={editAsset
  ? <LocalImageCropView key={editAsset.id} asset={editAsset} … />
  : undefined}
```

外壳不能挂 `key={asset.id}`：换一张图就把它整个卸掉重建，等于让合成器把整窗重新栅格化一遍，连续翻页时最明显。外壳内部本来就按 `src` 变化复位缩放/旋转，不需要靠 remount。

编辑器则要挂：它带着「这次编辑的初始状态」（旋转、翻转、裁剪框、撤销历史），换一张素材必须是一份干净状态，不能沿用上一张的撤销栈。

同一个外壳里，**状态归属不同的组件，存活策略就该不同**。

## 验证清单

静态检查：

```bash
cd renderer && npx tsc --noEmit
```

手工验证（这张清单比「看着不闪了」可靠）：

1. 大图进入裁剪：图片无尺寸变化、无空白帧、无转圈胶囊弹出；
2. 裁剪里点关闭：图片立即完整，不出现「半张」；
3. 编辑中按 Tab：焦点不会落到被隐藏的顶栏按钮（`invisible` 把它们移出了 Tab 序）；
4. 编辑中点击预览区域：没有翻页箭头响应（隐藏层是 `pointer-events-none`）；
5. 连续上下切图再进裁剪：缓存命中，仍然不闪。

## 边界与代价

- **只对不透明的 overlay 成立**。现在的做法是「保留 + 藏起来」，前提是盖在上面的视图自己铺满且不透明。以后要是加带背景模糊/半透明的面板，要么给它一个不透明底，要么另做交叉淡入，不能直接复用 `invisible` 分支。
- **缓存上限 4 张**。`HTMLImageElement` 被引用着，就等于解码位图常驻内存；翻页快的时候留多了不划算。
- **超大图的一次性开销**。`drawImage` 把 6000px 缩到 1300px，即使 `imageSmoothingQuality: 'high'`，也是主线程上几十毫秒的活。因为放在 layout effect 里，它会在首帧绘制前阻塞——换来的是「不闪」，代价是「进入可能略慢一两帧」。这笔交换在这个场景里是划算的。
- **缓存未命中仍会闪一帧**。兜底路径是占位图 + 异步加载；要彻底消除，得把预热提前到 `onPointerDown`（按下「裁剪」那一刻就把 URL 塞进缓存）。目前没做，因为实测命中率是 100%。

## 几点可以带走的结论

1. **共用外壳的子视图切换，不要卸载内容。** 卸载的代价不是「重新挂载一个 DOM」，而是「重新解码 + 重新栅格 + 重新合成」。
2. **需要「首帧就有」的测量与绘制放 `useLayoutEffect`。** `useEffect` 天然晚一拍，这一拍就是用户看到的那一帧空白。
3. **元素级解码缓存比 HTTP 缓存管用。** 缓存再热，`onload` 仍是异步任务；能同步拿到的，只有「已经解码完的那个元素」。
4. **切视图的闪，先查几何，再查时序。** 尺寸不一致的「跳一下」和时序错位的「空一帧」，肉眼上很像，但成因和修法完全不同。
5. **同一属性不要写两个 Tailwind 工具类。** 生效顺序由生成顺序决定，不由你写的顺序决定。
6. **用「进/出哪一侧才闪」做第一步定位。** 退出闪 = 卸载问题；进入闪 = 挂载问题；两边都闪 = 大概率是外壳本身在重建。
