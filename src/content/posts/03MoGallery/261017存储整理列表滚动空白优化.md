## 现象

后台「存储整理」（`/admin/storage`）的文件列表，**滚动快一点就整片空白**——不是「行渲染出来了但图片没加载」，而是行本身不见了：没有文件名、没有分隔线、没有任何占位，就是一大块背景色。慢滚、或者停下等一会儿，内容才「刷」地冒出来。

用户的原话是：*发现列表如果滚动过快，会出现这种区域空白的情况*。

这种空白有个很典型的特征：**它不是 bug 意义上的「没渲染」，而是浏览器来不及画**。所以第一反应不该是「数据没请求到」，而该怀疑主线程在滚动的关键帧里被别的东西占住了。

## 排查：先排除三个错误的怀疑方向

按常规套路先查了三件事，全部证伪：

| 怀疑方向 | 检查方式 | 结论 |
| --- | --- | --- |
| 双滚动容器打架 / 滚动到底部提前结束 | 从 admin layout 一路追到列表容器 | 只有一层 `overflow-y-auto`，`.flex h-screen overflow-hidden` 的外壳不滚动，排除 |
| CSS 层的问题（`will-change`、`translateZ`、`content-visibility`） | 全仓库 grep | `will-change` / `translateZ(0)` 只作用于 `input[type=range]`；`content-visibility` 只出现在 story、blog 的列表里，存储页完全没有 |
| 已经有虚拟化但参数配错了 | grep `useVirtualizer` / `overscan` / `translateY` | **整个存储页没有任何虚拟化**，`visibleFiles.map()` 直接全量铺进 DOM |

第三行就是问题的一半。S3 桶实测 **414 行**，满桶能到 **850+**，全部常驻 DOM，列表总高两万五千像素以上。

## 真正的原因：两个，叠在一起

### 其一：44px 的预览位拉的是原图

列表每行最左边有个 `size-11`（44px）的预览方格：

```tsx
function FileThumb({ file, onClick }: { file: StorageFile; onClick: () => void }) {
  const showImage = isImageFile(file.key) && Boolean(file.url) && !failed
  // ...
  <img src={file.url} loading="lazy" className="size-full object-cover" />
```

`file.url` 是**对象存储里的原图**。这批照片大多是 1–3MB、约 4096×3072，也就是一千万像素级。为了画一个 44px 的小方块，浏览器要完整下载、完整解码一张千万像素 JPEG。

`loading="lazy"` 让人误以为这是安全的——实际上它只保证「不在视口就先不加载」，而快速滚动时视口是**连续不断**地进入新内容，一次性解除几十上百个懒加载，解码任务全堆到主线程上。图片解码（尤其大图缩小）在主线程上的开销，足够让后续的栅格化排队到下一帧、再下一帧。

### 其二：全量 DOM 让布局成本也集中在关键帧

400+ 行常驻 DOM，滚动本身不便宜；再叠加每行一张大图解码，就出现了 Chromium 的 checkerboarding——**来不及栅格化的区域先涂背景色**，等主线程空了再补。这正好解释了「停下就恢复」这个特征。

所以这不是一个 bug 修一个点，是**两条都要收**：图片从 MB 级降到几十 KB，DOM 从 400+ 行降到视口量级。

## 方案一：让缩略图真的是缩略图

### 服务端已经算出了缩略图，只是没往列表里带

查代码时发现一个挺讽刺的事实：缩略图**一直存在**。上传链路里 `server/lib/storage/s3.ts` 就有 `result.thumbnailUrl = this.getUrl(thumbKey)`；扫描时也用 `photo.thumbPath` 判断出了 `hasThumb` 状态。唯独列表接口的返回结构里没有地址：

```ts
// server/lib/storage/types.ts —— 列表用的 StorageFile
export interface StorageFile {
  key: string
  size: number
  lastModified: string
  url: string
}
```

`thumbnailUrl` 只在 `UploadResult` 上有。于是前端只能拿到 `url`，只能拉原图。

### 改动：扫描接口多返回一个字段

`hono/storage.ts` 里 `FileWithStatus` 加上可选字段，并在拼装每一行时补上：

```ts
return {
  key: file.key,
  url: file.url,
  // 缩略图必须真实存在于存储里才给地址，否则前端会去拉一个 404
  thumbnailUrl: hasThumb && photo?.thumbPath ? storageProvider.getUrl(photo.thumbPath) : undefined,
  size: file.size,
  // ...
}
```

这里有个容易写错的地方：**不能无条件拼出地址**。扫描结果里本来就有「缩略图缺失」的行（`missing_thumbnail` 状态），如果对这种行也返回一个 URL，前端就会去请求一个确定 404 的地址，白白多一轮失败请求 + 控制台噪音。所以条件是 `hasThumb && thumbPath` 双满足。

### 前端：三级回退，且按「地址」而不是「布尔量」记失败

前端**没有动共享包**。`StorageFile` 在 `packages/api-client` 里是 `mo-gallery-shared` 的镜像，为一个纯附加的可选字段去改共享包，会牵扯两个消费方的同步和提交，不划算。用一个交集类型就能绕开：

```ts
/**
 * 扫描结果的一行。服务端在 StorageFile 之上额外附了 thumbnailUrl，
 * 这里按交集类型声明，避免为这一个可选字段去动共享包 api-client。
 */
type ScanFile = StorageFile & { thumbnailUrl?: string }
```

`FileThumb` 改成缩略图优先、原图兜底、两者都不可用才落占位图标：

```tsx
function FileThumb({ file, onClick }: { file: ScanFile; onClick: () => void }) {
  const [thumbFailed, setThumbFailed] = useState(false)
  const [originalFailed, setOriginalFailed] = useState(false)

  // 44px 的预览位优先用缩略图（几十 KB）；缩略图缺失或加载失败才回退到原图。
  const src = file.thumbnailUrl && !thumbFailed ? file.thumbnailUrl : file.url

  return (
    // ...
    <img
      src={src}
      loading="lazy"
      decoding="async"
      onError={() => { if (file.thumbnailUrl && !thumbFailed) setThumbFailed(true); else setOriginalFailed(true) }}
      className="size-full object-cover"
    />
  )
}
```

两个细节值得说明：

- **记「哪个地址失败了」而不是一个 `failed` 布尔量**。如果只记一个布尔量，缩略图 404 会直接把整格弄成占位图标，哪怕原图是好的；更麻烦的是后台重新生成缩略图之后，这个布尔量不会自己复位，列表会一直显示占位。分开记，重新生成后刷新就能恢复。
- **`decoding="async"`**。它允许浏览器把解码从渲染的关键路径上挪开。单张图省不了多少，但滚动时是几百张图同时排队，这个提示有实际收益。

单格图片从 MB 级降到几十 KB，主线程的解码压力基本消失。

## 方案二：列表虚拟化

### 第一步我手写了一个 hook，然后被 eslint 教育了

最初想的是「不引依赖，固定行高窗口化就够」：以第一行的实测 `offsetHeight` 作行高、`requestAnimationFrame` 合并滚动事件、`ResizeObserver` 跟容器高度、上下两条留白撑住完整滚动高度，只把视口上下各 10 行放进 DOM。

功能是对的，DOM 从 400+ 行降到 30 行左右。但第一版把 ref 和渲染期要读的数字塞进了同一个返回对象：

```ts
// ❌ 这样写会被 react-hooks/refs 规则抓出来
return { scrollRef, start, end, paddingTop, paddingBottom, measureRow }
```

新的 `eslint-plugin-react-hooks` 的 `react-hooks/refs` 规则报了 **10 个错**：`Cannot access refs during render`、`Passing a ref to a function may read its value during render`——因为组件在 render 期间读了 `rowWindow.start`，而那个对象里混着 ref。

改成**返回元组**、把「ref」和「纯状态对象」彻底分开就好了：

```ts
const [listScrollRef, rowWindow] = useRowVirtualizer({ count: visibleFiles.length })
```

> 教训：自定义 hook 只要同时返回 ref 和「渲染期要用的数值」，就一定会踩 `react-hooks/refs`。要么返回元组，要么把 ref 单独用一个函数暴露。

### 第二步：换成 react-virtuoso

修好之后问了一句：*还是会有这个问题，有没有什么开源组件/方案解决？*——确实该用成熟库。对比了一下：

| 方案 | 适配度 | 说明 |
| --- | --- | --- |
| `react-virtuoso` | **选它** | 有 `scrollSeek` 机制：快速滚动时先渲染指定的占位内容，而不是留白——和这个现象一一对应 |
| `@tanstack/react-virtual` | 备选 | 更通用、更底层，动态行高靠 `measureElement`；手写那套逻辑基本就是它的子集 |
| `virtua` | 备选 | 更轻，但生态和文档量级小一档 |

选了 `react-virtuoso`（`^4.18.19`），把手写的 hook 整个删掉：

```tsx
<Virtuoso
  data={visibleFiles}
  computeItemKey={(_, file) => file.key}
  increaseViewportBy={{ top: 600, bottom: 900 }}
  itemContent={(_, file) => <FileRow key={file.key} file={file} />}
/>
```

`increaseViewportBy` 是给滚动方向做预热——上下各留一段缓冲区先渲染好，滚过去时就已经在 DOM 里了。

另外补了一个容易被忽略的细节：列表在**数据源 / 状态 / 搜索 / 目录筛选**变化时要重建（`key` 由这四项组成），否则虚拟化容器会保留旧的滚动偏移，切换后停在新清单的中段，看着像「没加载出来」。

### 交互口径没有变

虚拟化只改渲染层。勾选、悬停出现的操作按钮、搜索 / 状态 / 目录筛选、批量清理——**全部仍然作用在完整数组上**，不是「只对可见行生效」。这点必须在实现时守住，否则一旦把 `visibleFiles` 换成 `slice` 后的结果，批量操作就会静默地只处理一部分，那是比空白严重得多的问题。

## 桌面端同步：同一处问题，两种源

Web 端修完后，桌面端的「存储整理」页面是同一个毛病（`frontend/src/pages/StoragePage.tsx` 的 `FileThumb` 也是 `src={file.url}`），于是照搬。但桌面端比 Web 端多一层复杂度：**它的存储源有两种**。

### Go 侧的 DTO 加一个字段

```go
type StorageObjectDTO struct {
    // ...
    ThumbnailURL string `json:"thumbnailUrl,omitempty"`
}
```

两种源走的是完全不同的路径：

- **Web 存储源**（连自部署站点）：`services/storage_web.go` 是 `/admin/storage/scan` 的**透明代理**，Web 端刚加的 `thumbnailUrl` 会随 JSON 直接解出来，Go 侧一行映射都不用写。这是先把 Web 端改掉的额外好处。
- **插件存储源**（S3 / WebDAV 等本地插件）：`services/storage_maintenance.go` 的 `Scan` 里建一张「本次列举拿到的 key → URL」的表，命中有归属的对象时反查缩略图自己的地址：

```go
if owner.HasThumb && owner.ThumbPath != "" {
    row.ThumbnailURL = urlByKey[owner.ThumbPath]
}
```

**为什么是反查，而不是按 key 自己拼 URL？** 因为缩略图本身就是那个存储源上的**一个普通对象**，它的可访问地址由插件决定：可能是公共 CDN 域名，可能是带签名的临时地址，也可能根本是本地磁盘路径。自己按 `publicUrl + "/" + key` 拼，就等于假设了一种源未必遵守的目录约定——拼错了不会报错，只会静默 404。

### 前端用仓库里已有的库

桌面端前端没有引入第二套虚拟化，而是用 `@tanstack/react-virtual`——**本地资源库的网格（`LibraryJustifiedRows`、`LocalAssetGrid`）本来就在用它**。再装一个 `react-virtuoso` 只会多一份维护面，而这里的列表是等高单行，`tanstack` 完全够用：

```tsx
const rowVirtualizer = useVirtualizer({
  count: visibleFiles.length,
  getScrollElement: () => scrollRef.current,
  estimateSize: () => 61,   // py-2 + size-11 + 1px，只影响首帧
  overscan: 12,
})
```

行改成绝对定位 + `translateY`，`measureElement` 按真实高度逐行校正（`estimateSize` 只是首帧的猜测，实测值会覆盖它）。同样加了「换源/换筛选回顶部」的 effect。

### 两端一个刻意的行为差异

| | 缩略图缺失时 |
| --- | --- |
| Web 端 | 回退显示**原图**（能看总比空白好） |
| 桌面端 | 保持既有的**橙色占位图标**（`missing_thumbnail` 状态的语义） |

这不是没统一，是桌面端原本就把「缩略图缺失」当成一个需要用户注意的状态（列表本身支持一键重新生成缩略图），给它看原图反而会掩盖问题。Web 端没有这个操作入口，所以选择能看就行。

## 验证

- Web：`pnpm exec tsc --noEmit` 只剩 3 个**改动前就有**的报错（`packages/ai-agent/zz-verify-tooloutput.ts` 的 BigInt 目标版本、`WeChatArticleTab.tsx` 两处参数个数）；`eslint` 相对 HEAD 无新增问题。
- 桌面端：`go build ./...` 通过；`pnpm exec tsc --noEmit` 零错误；`wails3 generate bindings -clean -ts` 重新生成后，绑定里只多出 `thumbnailUrl` 一处（另外几个文件的 diff 是别的改动带来的存量漂移）。
- 最终以「实际滚起来不空了」为准——这类渲染问题，静态检查只能保证不写错，观感必须人眼看。

## 小结

1. **一个 44px 的框拉原图，是在用流量和解码时间换一行代码的省事。** 缩略图的职责就是小，只要存储里有，就应该走它；没有才回退。
2. **虚拟化和图片优化是两件事，别指望一个解决另一个。** 图片压下去能缓解，但 400+ 行的布局成本还在；虚拟化能把 DOM 降到视口量级，但如果每行仍在解码千万像素大图，主线程照样堵。两个一起收才干净。
3. **失败状态要记「哪个地址失败」，不要记「失败了」。** 前者能自愈，后者会永久降级。
4. **虚拟化只该改渲染层。** 任何「只对可见行生效」的副作用（批量选、批量删）都是严重回归，比空白难查得多。
5. **先看服务端已经算了什么。** 这次最省力的部分就是发现 `hasThumb` 早就算出来了，只差一个字段没往外送。
