---

### 一、什么情况要 GPU 调度？（Why & When）

GPU 与普通 CPU/内存调度的最大区别在于：**单卡极其昂贵、显存不可超卖（OOM 直接宕掉进程）、计算单元（SM）并行度极高、且多卡间极度依赖物理通信拓扑（NVLink / InfiniBand）**。通常在以下 5 种场景下必须引入 GPU 调度：

#### 1. 资源昂贵与利用率低（显存/算力严重闲置）
* **算力空转**：开发调试（JupyterLab）、轻量推理或前处理/后处理阶段，GPU SM 利用率往往长期低于 15%。
* **显存碎片化**：任务 A 占了 20GB 显存，剩下 60GB 无法分配给其他小任务，导致整卡被独占锁定。

#### 2. 多租户混部与优先级冲突（Multi-tenancy & Co-location）
* **在线 vs 离线**：线上实时推理业务（低延迟要求、流量有潮汐波峰波谷）与离线大模型预训练/微调任务（高吞吐、跑几天几周、对单次延迟不敏感）共用一个集群。
* **部门间配额与抢占**：算法团队需要资源隔离、Quota 保障；低优先级任务在集群闲置时自动借用卡，高优先级任务到达时需快速驱逐或抢占。

#### 3. 大模型分布式训练/推理（拓扑敏感场景）
* LLM 训练和 Serving 通常涉及张量并行（TP）、流水线并行（PP）、数据并行（DP/ZeRO）。
* **拓扑盲区灾难**：如果把同一个 TP 组的两张卡调度在同一台机器但**不在同一个 NVLink 树**下（跨了 PCIe），或者跨节点调度到**不同机柜交换机（Spine-Leaf 跨层）**，通信延迟会暴涨数倍，拖垮整个集群。

#### 4. 分布式任务的“全有或全无”（Gang Scheduling 需求）
* 分布式训练（如 8 节点 64 卡）要求所有 Worker 同时启动并建立 All-Reduce 通信环。
* 普通调度器（如原生 K8s 逐 Pod 调度）容易出现：任务 A 抢了 4 卡，任务 B 抢了 4 卡，两者互相等待另外 4 卡释放，导致**集群死锁（Deadlock）**。

#### 5. 硬件高故障率与容错迁移
* 大规模集群中，GPU 坏卡、显存 ECC 翻转、NVLink 掉速属于常态。调度系统需要配合健康检查，实现故障节点自动排空、任务快速断点续训（Checkpoint Resume）与热迁移。

### 二、如何做 GPU 调度？（How）

工业界通常采用**三层垂直分层**的调度体系：

```text
┌────────────────────────────────────────────────────────┐
│ 3. 应用/运行时调度 (LLM Serving, Batching, Pipeline)   │  vLLM / TensorRT-LLM / Ray
├────────────────────────────────────────────────────────┤
│ 2. 集群与编排调度 (拓扑感知, Gang, 资源配额, 抢占)      │  K8s + Volcano / HAMi / Slurm
├────────────────────────────────────────────────────────┤
│ 1. 硬件与驱动切分 (算力/显存虚拟化, 隔离)               │  MIG / MPS / vGPU / cGPU
└────────────────────────────────────────────────────────┘
```

---

#### 1. 硬件与驱动层：如何“切分”一张 GPU？

单卡无法满足多任务隔离时，底层的切分与虚拟化手段：

| 方案 | 原理 | 隔离性 | 适用场景 |
| :--- | :--- | :--- | :--- |
| **NVIDIA MIG** (Multi-Instance GPU) | 在硬件硅片级把 GPU（A100/H100）切分为独立的硬件实例（SM、显存、交叉开关完全物理隔离）。 | **硬件级强隔离**（互不影响，极其安全）。 | 强隔离多租户、公有云、严禁抖动的生产推理。缺点是切分粒度固定（如分成 7 份）。 |
| **NVIDIA MPS** (Multi-Process Service) | 多个 CUDA 进程共享同一个 CUDA Context，利用硬件 Hyper-Q 并发执行不同进程的 Kernel。 | **软隔离**（显存可设上限，但无硬件故障隔离，一个崩全部崩）。 | 小模型低延迟在线推理，填满 SM 空隙。 |
| **CUDA Hook / vGPU**（如阿里 cGPU、开源 HAMi、vCUDA） | 在用户态通过动态链接库劫持（`dlsym`）拦截 `cudaMalloc`、`cudaLaunchKernel` 等 API，通过 Token 桶控制显存分配与算力使用率。 | **驱动级/用户态隔离**（灵活度极高，可按 1% 算力、100MB 显存任意切）。 | 算法开发环境、高校/企业内部分时复用。 |

---

#### 2. 集群与系统层：如何做资源协同与调度？

针对 Kubernetes 或 HPC 集群的调度系统关键设计：

##### (1) 拓扑感知调度（Topology-Aware Scheduling）
* **节点内拓扑**：调度器通过读取 `nvidia-smi topo -m` 或 NVML，构建 GPU-PCIe-NUMA-NVLink 的加权无向图。调度分布式任务时，优先绑定在同一个 **NVLink Clique** / 同一 CPU Socket 下。
* **网络织物拓扑（Fabric Topology）**：调度器需要感知机柜交换机（TOR Switch），尽量将跨节点的通信紧密型任务（如 TP/PP 组）调度在**同一交换机下的同一机架**内。

##### (2) 批调度与防死锁（Gang Scheduling / Coscheduling）
* 采用 **Volcano**、**Kube-batch** 或 **Ray Core**。
* 设置最小就绪数量 `minAvailable`：一个大模型分布式作业需要 64 卡，只有当集群能同时腾出 64 卡时才一次性绑定（All-or-Nothing），否则任务排队等待，避免局部锁死。

##### (3) 优先级与弹性抢占（Elastic Preemption）
* **混部策略**：白天流量高峰，在线推理任务以高优先级运行；夜间流量低谷，自动缩容推理实例，调高离线训练任务 Quota。
* **秒级抢占**：在线任务扩容时，调度器向低优先级离线任务发送 `SIGTERM`，给其 30-60 秒保存最新 Checkpoint，随后强行驱逐释放 GPU。

---

#### 3. 应用与运行时层：大模型专属的高性能请求调度

在进入 GPU 之后，针对 LLM 推理与训练的应用级调度是近两年的核心突破点：

* **连续批处理（Continuous Batching / Iteration-Level Scheduling）**：
  * *传统调度*：整批 Request 一起进、一起出，短文本必须等待长文本生成完毕，产生大量 Padding 浪费。
  * *现代引擎（vLLM / TGI）*：调度粒度从“请求级”下沉到“Token 迭代级”，每个解码 step 动态插拔已结束和刚到达的请求，SM 利用率提升 3-5 倍。
* **PagedAttention（显存分页调度）**：
  * 模仿 OS 虚拟内存分页，将 KV Cache 切分为离散的物理 Block，动态分配，解决显存碎片化并支持 Prefix Caching 共享。
* **Prefill / Decode 解耦调度（PD 分离）**：
  * **Prefill 阶段**属于计算密集型（吞吐高、Compute-bound）；
  * **Decode 阶段**属于访存密集型（单 Token 延迟敏感、Memory-bound）；
  * 调度器将 Prefill 和 Decode 拆分到不同的专属 GPU 节点上，通过高速网络（RDMA/NVLink）传输中间 KV Cache，大幅提升吞吐并降低 TTFT（首字延迟）。

### 总结选型建议

| 阶段 / 规模 | 核心诉求 | 推荐技术栈 |
| :--- | :--- | :--- |
| **小团队 / 研发实验** | 避免卡被单人占死，多人在同一张卡上调试 | K8s + **HAMi** (vGPU 显存切分) + JupyterHub |
| **生产大模型推理** | 高吞吐、低延迟、动态高并发 | **vLLM / TensorRT-LLM** + K8s HPA + 拓扑亲和调度 |
| **大规模集群混合运营** | 离线训练与在线推理混部、千万级资产利用率 | K8s + **Volcano** (Gang / 拓扑调度) + MIG 硬件隔离 + RDMA/RoCE 感知 |
