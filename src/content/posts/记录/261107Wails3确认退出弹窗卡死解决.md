# Wails 3 确认退出弹窗卡死：排查与修复

MyGit 有一个退出确认弹窗。点击窗口关闭按钮后，弹窗正常出现；选择“退出程序”，窗口却不再响应。这个现象一开始很像是退出时机的问题，但把 `App.Quit()` 延迟 100 毫秒仍然卡住。后来对照“记住选择、下次直接退出”的路径，才发现两种退出走的并不是同一条链路。

## 两条退出路径

不再显示确认弹窗时，Wails 收到原生窗口关闭事件，进入 `WindowClosing` 钩子。应用检查到用户已经确认过，就放行这次关闭，窗口按正常流程销毁。

确认弹窗则是前端自己显示的。原来的实现是在前端调用 Go 服务 `ResolveClose`，后端设置允许退出的标记，然后调用 `App.Quit()`。这发生在一次尚未返回的前端 RPC 中：Wails 需要同步切回主线程销毁窗口，而窗口销毁又会触发服务清理。前端调用和窗口销毁因此交错在同一条退出链路里。

Wails 的生命周期实现里，退出时会同步执行服务的关闭钩子；如果其中某项清理阻塞，窗口也会一直等着。延迟 100 毫秒只能碰运气让 RPC 先返回，不能保证退出顺序正确，所以实测没有解决问题。

## 排查终端清理

应用退出时也会关闭集成终端。Windows 版终端运行在 ConPTY 里，原先的清理逻辑只结束 shell 进程，随后同步关闭伪终端。如果 shell 启动的子进程仍附着在 ConPTY 上，关闭伪终端可能等待子进程退出。这条路径有机会阻塞同步的服务关闭，因此也值得处理。

现在 Windows 终端关闭会用 `taskkill.exe /PID <pid> /T /F` 结束 shell 及其子进程，并限制等待时间。如果结束进程树失败，则回退为结束 shell；此时不在窗口关闭线程上同步关闭 PTY，而是让进程等待协程在 shell 退出后收尾。

这部分有针对性测试：启动 PowerShell 和持续运行的 `ping -t 127.0.0.1`，再关闭终端，检查清理能否在限定时间内完成。测试能覆盖子进程仍附着时的清理场景，但它不能单独证明这就是确认退出卡死的根因。

## 让确认退出复用原生关闭流程

修复重点是让确认弹窗和直接关闭最终走同一条 Wails 窗口关闭路径：

1. 前端选择“退出程序”后，先调用 `ResolveClose`。
2. 后端记录本次退出已获确认，然后正常返回，不在 RPC 内调用 `App.Quit()`。
3. 前端确认 RPC 成功后调用 Wails 的 `Window.Close()`。
4. 原生 `WindowClosing` 钩子再次检查退出标记，看到已经确认便放行窗口关闭。

如果 RPC 失败，前端不会继续关闭窗口。这样既保留了确认弹窗，也复用了直接关闭时已经验证过的生命周期入口，不再依赖 100 毫秒定时器。

另外，用户测试直接关闭时还观察到一个终端窗口闪现后消失。结合退出时新增的 `taskkill.exe` 调用，它很可能是子进程启动时短暂显示的控制台。调用前给该子进程应用现有的 `hideConsole` 配置，同时设置 `HideWindow` 和 `CREATE_NO_WINDOW`，避免显示控制台窗口。这个解释与现象吻合，但是否就是闪窗的唯一来源，还需要在目标环境复测。

## 验证情况

修改后，前端 `npm run check` 通过，`npm test` 通过（3 个测试文件、39 个测试）；Go 服务测试通过，Windows 定向测试也通过。定向测试覆盖了 taskkill 子进程树清理，以及隐藏控制台所需的进程标志。使用 Wails 3.1.0 执行 `go tool wails3 build` 成功，生成了新的 Windows 构建 `bin/MyGit.exe`。

这些结果说明代码检查、测试和打包都通过了；它们还不能代替桌面环境里的实际退出验证。接下来需要用新构建确认两件事：从弹窗选择“退出程序”后窗口正常关闭；直接关闭时不再出现控制台闪窗。
